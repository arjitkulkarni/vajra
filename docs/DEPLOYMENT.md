# Deploying VAJRA

Two hosts, because the two halves are different shapes.

| Half | What it is | Where it goes |
|---|---|---|
| `apps/web` | A Next.js build — static pages, SSR routes, the camera work in the browser | Vercel |
| `apps/gateway` | A process: a Fastify listener, the outbox worker that anchors audit events, an embedded Postgres, a content-addressed asset store | Render, from [render.yaml](../render.yaml) — or any host that runs Node |

The two URLs point at each other. `NEXT_PUBLIC_GATEWAY_URL` sends the browser to the gateway;
`WEB_ORIGIN` is the gateway's CORS allowlist and the origin it builds the admin console link from.
Change one and change the other.

## The gateway, on Render

1. Render → **New** → **Blueprint** → this repository. It reads [render.yaml](../render.yaml):
   Node 22, `pnpm install --frozen-lockfile --filter @vajra/gateway...`, then
   `pnpm --filter @vajra/gateway start`, with `/v1/health` as the health check.
2. Set **`WEB_ORIGIN`** — the only variable the blueprint leaves for you, because only you know
   where the web app landed. Comma-separated if you want preview origins too.
3. The four secrets (`SESSION_JWT_SECRET`, `MASTER_KEK`, `PROOF_SIGNING_SEED`,
   `ADMIN_CONSOLE_SECRET`) are generated by Render and never leave it. Rotating
   `ADMIN_CONSOLE_SECRET` revokes every console link handed out before it; rotating `MASTER_KEK`
   makes assets already in the store unreadable.
4. Check it: `curl https://<service>.onrender.com/v1/health` answers `"ok": true` and names every
   mode it is running in. The admin console link is printed in the service's logs at boot.

**What the free plan forgets.** The service sleeps after 15 minutes idle — the next request pays a
cold start of roughly a minute — and its filesystem is ephemeral. The embedded database and the
asset store therefore come back empty *together*, and `DEMO_MODE=true` reseeds them at boot, so the
state is always coherent, just young. For a judged demo, wake it before you present.

**Making state last.** Add a Render Postgres and set `DB_MODE=postgres` with its `DATABASE_URL`,
*and* attach a disk for the asset store with `STORAGE_DIR` pointed into the mount. Do both or
neither: a database that survives a restart while the asset store does not leaves audit rows and
passports referring to content that is gone.

Any other Node host works the same way — the build and start commands in the blueprint are the whole
contract, and `PORT` is read from the environment.

## The web app, on Vercel

Project settings:

- **Root Directory** → `apps/web`. If a project is currently pointed at `apps/gateway`, this is the
  setting to change — see the last section for why that deployment cannot work.
- **Framework Preset** → Next.js (detected).
- Leave **Include source files outside of the Root Directory** on: the workspace packages the app
  imports live at `../../packages`.

Environment variables:

| Variable | Value |
|---|---|
| `NEXT_PUBLIC_GATEWAY_URL` | `https://<service>.onrender.com` |
| `NEXT_PUBLIC_LIVENESS_MODE` | `simulated`, or `faceapi` with the weights step below |
| `NEXT_PUBLIC_LIVENESS_MIN_SCORE` | `0.45` |
| `NEXT_PUBLIC_LIVENESS_ENFORCE` | `block` |

**Face model weights.** `apps/web/public/models` is gitignored — the AdaFace backbone alone is about
174 MB — so a deployed build ships without weights and the capture falls back to simulated evidence,
badged as such. To run the real check on the deployed site, override the build command:

```
pnpm models:fetch && pnpm --filter @vajra/web build
```

That downloads the weights into the build every time, which is slow but honest. `simulated` is the
right choice for a link you are handing out casually.

## Why the gateway is not on Vercel

It was tried; it 500s on every request with `ERR_MODULE_NOT_FOUND`. The immediate cause is that the
start command runs through `tsx` and the workspace packages ship TypeScript source, so a pruned
function bundle cannot load them. The real reason is the shape: [`server.ts`](../apps/gateway/src/server.ts)
calls `listen()`, starts the outbox worker, and seeds a demo database at boot, and it holds the
hash-chained ledger and the asset store on disk. A serverless invocation is a fresh, read-only
filesystem — the chain would reset between requests, uploads would fail outright, and nothing would
ever drain the outbox. The typecheck passing is not the same as the thing being deployable there.
