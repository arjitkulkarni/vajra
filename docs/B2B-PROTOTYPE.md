# VAJRA as a B2B product
*The complete ideation and build plan — from SIH prototype to pilot-ready custody control plane.*

## 0. The twenty-five locked decisions

Every irreversible choice this plan commits to, in one page. Where two approaches conflicted, one was picked and the reason is in the clause.

1. **The vertical is media & entertainment pre-release content security** — the studio-to-vendor boundary (post, VFX, localization, dubbing, dailies) — chosen over defence/aerospace and life sciences purely on procurement velocity: a published ~100-control gauntlet (MPA Content Security Best Practices / TPN), a buyer who can sign inside one quarter, and a trigger event with a date on it.
2. **The primary paying ICP is the Tier-1/Tier-2 post/VFX/localization facility** (200–800 seats; Mumbai, Chennai, Bengaluru, Manila, London, Toronto), buying against a conditional or failed TPN assessment; the studio/streamer content-security org is the *mandating* buyer sold second, and the facility-side value must stand alone with no studio in the picture — that is written into the pilot success criterion and tested in the first three sales calls.
3. **The wedge is controlled egress of a single title from a single facility**: one production, one asset class (masters/plates/deliverables), one action pair (`asset.download` / `asset.export`), one control (WebAuthn step-up plus a second distinct attested approver), one artefact (a per-title Chain-of-Custody Evidence Pack the studio verifies offline).
4. **VAJRA is a custody control plane, never a data plane.** The Custody Broker (`POST /v1/custody/checkout` → receipted, time-boxed, single-use presigned URL against the customer's own S3/Wasabi/B2/MinIO bucket; `POST /v1/custody/complete` closes the receipt) means bytes never enter the Node process. The existing encrypted vault is retained only for small artefacts (<5 GB). This deletes the 25 MB cap and the chunked-streaming-encryption project as product questions rather than scheduling them.
5. **Tenancy is shared-schema, pooled-database, row-level isolation enforced by Postgres RLS** — chosen over schema-per-tenant and database-per-tenant because PGlite is a single embedded connection and transaction-local `set_config('vajra.tenant_id', $1, true)` is the only seam that behaves identically on PGlite and pooled Postgres. Dedicated-database is a paid tier served by the identical schema, never a fork.
6. **Tenancy has two axes: `tenants` (a facility) is the hard security boundary, `projects` (a title/production) is the need-to-know boundary inside it** — the project axis is not gold-plating, it is precisely what the studio contracts for and what TPN assesses.
7. **Chain serialisation uses `tenant_chain_heads(tenant_id, seq, chain_hash)` taken `FOR UPDATE` inside the writing transaction, plus `tenant_counters` upserts for all business identifiers — NOT the two-int `pg_advisory_xact_lock(4242, hashtext(tenant_id))` form** that three of four blueprints proposed; row locks are transactional, visible in `pg_locks`, avoid the one-int/two-int namespace hazard on any rolling deploy, and kill the racy `COUNT(*)` identifier minting in the same change.
8. **The audit payload commits identifiers as HMAC-SHA256(subject_salt, value), never cleartext** — the three-tier erasure model (Tier C chain hashes / Tier B salted identifier commitments / Tier A ciphertext + wrapped DEK) lands in the *same* breaking change as chain v2, before any pilot data exists, because it changes what enters the hashed payload and cannot be retrofitted.
9. **The chain is versioned, never rehashed**: existing rows stay `chainVersion: 1` and verifiable under v1 rules forever; every tenant gets a fresh v2 genesis with a signed crossover record; `tenant_id` lives in a column outside the v1 hashed payload.
10. **Identity is federated: OIDC Authorization Code + PKCE plus SCIM 2.0, with Microsoft Entra ID certified end to end and Okta described as best-effort on the same code path.** WebAuthn passkeys with server-checked UV replace the client-asserted liveness path; `assurance_level` (hardware | platform | simulated) becomes a first-class policy condition and `simulated` is refused outside the sandbox tenant.
11. **`packages/dev-idp` — a small in-process OIDC provider mounted only under the laptop profile — lands and turns the 35 unit tests and 56 e2e assertions green in an EARLIER commit than the one that deletes `/v1/demo/*`.** The laptop demo then exercises the same OIDC code path as Entra rather than a bypass.
12. **The ledger claim is a per-tenant signed hash chain plus hourly chain-head publication into Sigstore Rekor (with an RFC 3161 TSA fallback).** Hyperledger Fabric is removed from the plan entirely — not demoted — because it requires Docker on a machine that has none, has no `configtx.yaml`/orderer/CA in the repo, one peer with no failover, and a health probe that can never report a dead peer while feeding the fail-closed gate. The `LedgerDriver` seam and the written-once-executed-twice property of `@vajra/chain-logic` are kept.
13. **Keys go behind a `KeyProvider` seam mirroring `StorageDriver`**, with drivers `local` (HKDF-SHA256 from a ≥32-byte key, refuses the shipped dev defaults outside the laptop profile), `awskms` and `azurekv`; per-tenant KEK, `kek_id` + `wrap_alg` per row, `kid` on every signed artefact, and BYOK in the customer's own AWS account as the answer to "who holds the key".
14. **Third-party offline verifiability is the moat and is never stubbed**: published per-tenant JWKS and `did.json`, `kid` resolution against retired keys, signature and issuer reported as two independent checks (backed by an issuer alias history), stapled anchor attestations instead of in-place re-signing, and a zero-dependency `@vajra/verify` package + static page released Apache 2.0 with no license key and no telemetry.
15. **`VAJRA_PROFILE` (laptop | vpc | saas | airgap) is the single configuration surface**, with a boot-time `assertProfileInvariants()` refusing to start on dev-default secrets outside laptop, demo or dev-IdP outside laptop, `fs`/`pglite` with replicas > 1, or `KEY_PROVIDER=local` outside laptop/airgap.
16. **Deployment topology order is: laptop (evaluation, shipped tier) → facility single-box VPC (the pilot topology, the only one that earns the first cheque) → studio-oversight SaaS. Air-gapped is explicitly deferred past the plan horizon** and sold as a roadmap item, not a deliverable.
17. **Everything the verdict depends on becomes a hashed, versioned `PolicyBundle` passed to `decide()` as an explicit argument** — action classes, `REQUIRED_DEPS`, role table, trust gates, risk weights, tier cut-points — shipped as the immutable `vajra-default-v1`; the trace and every certificate cite `bundleHash` + `engineVersion`, and `decide()` stays pure, synchronous and I/O-free.
18. **Policy conflict resolution is total and safety-biased: deny > require_approval > step_up > allow, then priority, then lexical `(key, version)`** — replacing today's resolution-by-database-row-order — and the fail-open dependency gate inverts to `=== true` with a total `Record` type.
19. **`policy.edit` and `identity.revoke` route through `decide()` via a single `enforce(principal, action, resource)` PEP helper**, so the two most dangerous actions in the system get step-up, two-person approval and a signed receipt instead of a bare `requireRole` string comparison.
20. **Notification ships before console polish.** Slack/Teams approval cards that deep-link into the WebAuthn step-up (never bypassing attestation), plus an event bus and SSE — because the two-person rule is the strongest control in the product and today literally nothing tells the approver a request exists.
21. **The console splits into four capability-gated surfaces at four densities — `/admin`, `/ops`, `/audit`, `/my` — fed by an expanded `/v1/me` capability set; a 403 renders as an explanation and never as an empty table.** The `.catch(() => [])` swallowing of authorization failures on six pages is deleted.
22. **Offboarding reassigns asset ownership to a named successor or a facility custody account as a first-class `asset_transfers` row with `reason='offboarding'`**, so revocation never strands assets on a DID nobody can sign for and the custody chain does not fork.
23. **Pricing is on attested users and titles under custody — never on storage, bandwidth, decisions, proofs issued, or deployment topology.** Land with a $45,000 / 12-week fixed-scope paid pilot (below the tender threshold, above the free-trial threshold) with one written testable success criterion and a pre-agreed conversion price. External counterparties and the verifier are free forever, because metering the receipt destroys the property the product is built on.
24. **Deleted outright, not flagged: all six `/v1/demo/*` routes, `demo_identities` and its source-literal-derived private keys, `wipeAll`/`resetDemo`, public self-registration with a client-chosen role, the browser-side `previewOutcome` shadow policy engine, the client-supplied `deviceFingerprintHash` trust path, the cross-tenant duplicate-content disclosure, IPFS/Pinata storage drivers, and `tsx` as the production runtime.** The scenario presets and outage drills survive, quarantined behind an authenticated, tenant-scoped `/ops/drills`.
25. **The compliance claim is bounded and never inflated**: SOC 2 Type I readiness plus an independent pen-test report plus the 22-table isolation matrix output plus the offline verifier is the pilot-stage evidence; the Type II observation window starts in week 1 and Type II is never implied at pilot signature. Cedar adoption is a written decision record only — the differentiator was never the rule grammar.

## 1. The thesis, the market, the wedge

### 1.1 What VAJRA is

VAJRA is a **custody control plane** for pre-release content. It does not store the master and it does not move it. It sits in front of the object store and the transfer tool a facility already runs, evaluates every egress of a master, plate or deliverable against a hashed, versioned **PolicyBundle**, forces a second distinct human — attested by a hardware authenticator the server actually checks — onto the high-value ones, brokers a single-use time-boxed capability against the customer's *own* bucket, and emits a **Proof-of-Action**: a signed receipt binding the verified human, the exact policy version and its spec hash, the content hash of the exact bytes released, and a position in a per-tenant hash chain anchored to a public transparency log.

The single decision that makes everything else in this document tractable is that VAJRA is a control plane and never a data plane. The current build is the opposite: `apps/gateway/src/routes/index.ts:179` materialises an upload with `await part.toBuffer()`, `apps/gateway/src/modules/vault/service.ts` encrypts the whole plaintext in one `aesGcmEncrypt` call, `apps/gateway/src/app.ts:81` registers multipart with `limits: { fileSize: 25 * 1024 * 1024, files: 1 }`, and `vault/service.ts:50` throws `file_too_large` above 25 MB. Masters are 50 GB to 2 TB. Making that path work means chunked framed envelope encryption, streaming `StorageDriver` I/O, and a streaming plaintext hash — a project nobody has budget for and nobody asked for. The **custody checkout** (`POST /v1/custody/checkout` returning a receipted, single-use, time-boxed presigned URL against the customer's own S3/Wasabi/B2/MinIO bucket; `POST /v1/custody/complete` closing the receipt) deletes that project as a *product* question. The existing encrypted vault survives for small artefacts under 5 GB — cut lists, deliverable manifests, scripts, key art — where it is genuinely the right tool. It also removes the objection that ends the first meeting: nobody has to put a studio's unreleased master on our box.

That choice buys the whole plan, and it costs exactly one thing, which is worth stating before a reader finds it. If bytes never enter the Node process, VAJRA cannot itself compute the content hash it binds into the receipt. The hash therefore has to arrive from somewhere the customer already trusts: the object store's own `ChecksumSHA256`, or the registration connector that walked the bucket once. The receipt says *this hash, asserted by this source, at this time*, and is honest about which — it is a custody claim over an identified object, not a proof that VAJRA read the bytes. Anyone who wants byte-level assurance can re-hash from their own storage and compare; the receipt is built so that comparison is a one-line check rather than an argument. The registration connector that makes this real is a substantial piece of work in its own right and is budgeted as such in S7 — it is a dependency of the thesis, not a free consequence of it.

### 1.2 The vertical, chosen on procurement velocity

The vertical is **media and entertainment pre-release content security** — the studio-to-vendor boundary: post, VFX, localization, dubbing, dailies. This is a choice about how fast money moves, not about technical fit.

Regulated life sciences is the better *regulatory* fit for a signed-receipt product — 21 CFR Part 11 and EU Annex 11 are practically a specification for what a Proof-of-Action is — but the entry gate is supplier qualification audit plus computer system validation (URS/FS/IQ/OQ/PQ) plus SOC 2 Type II. That is a six-to-nine-month cycle a prototype cannot enter. Indian defence and DPSU supply chain matches the team's geography and the repo's original framing, and has an eighteen-month procurement with price-crushing tenders at the end of it. Media has three properties neither of those has: a **published control gaunttlet** of roughly a hundred controls (MPA Content Security Best Practices, assessed through TPN), a **buyer who can sign inside one quarter** because the spend is a cost of doing business rather than a capital programme, and an **existential trigger event** — a leak, or an assessment report that comes back with open findings a studio reads before it awards the next slate. TPN is not a pass/fail certificate and we should never sell it as one; the buying pressure comes from a report a customer is about to read, which is enough.

The spine is portable. Tenant maps to supplier facility, project maps to programme, studio maps to prime; if the first three sales conversations say media is wrong, controlled-technical-data release is the same product with different nouns.

### 1.3 The ICP and the economic buyer

Two buyers, sold in that order.

The **mandating buyer** is the VP or Director of Content Security at a studio or streamer, reporting to the CISO or Head of Post. Budget line: content protection opex — the same line that already funds forensic watermarking, TPN assessments and site audits. Their pain is that they cannot answer their own General Counsel's first three questions after a leak, and that they sign vendor agreements containing chain-of-custody clauses they have no instrument to enforce or verify.

The **paying buyer who closes fastest** is the Managing Director or Head of Technology at a Tier-1/Tier-2 post, VFX, localization or dubbing facility — 200 to 800 seats, in Mumbai, Chennai, Bengaluru, Manila, London or Toronto. Budget line: "client security requirements / TPN remediation," approved by two or three people with no committee. The economic buyer is the MD; the technical champion is the Head of Security or IT; the blocker is the pipeline lead who owns ShotGrid and the storage.

On budget size, the honest position is that our working numbers — order $2–8M/yr of content-protection opex at a major, $300k–1.5M at a mid-size studio or a streamer's regional content org, and a low-six-figure remediation envelope at a Tier-1 facility — are **assumptions carried at stated confidence, not researched figures**. They are the first thing the first three sales calls are instrumented to test, alongside the mandate question in §1.7. If the facility-side envelope turns out to be a tenth of that, the pilot price is wrong and the packaging in S8 changes; better to find that in week two than at signature.

**The pain, with a number.** After a leak, a studio runs weeks of manual forensic archaeology across a dozen or more vendors' incompatible MAM and transfer logs, and still cannot prove the record was not edited. On the facility side the number is a recurring assessment finding: shared artist accounts on shared workstations, no documented approval on egress, incomplete asset tracking — the same three findings, year after year, each remediated with a spreadsheet. Losing one streamer's slate is a seven-figure revenue event. The buying trigger is fear with a date, not a roadmap conversation.

### 1.4 The wedge

**Controlled egress of a single title from a single facility.** One production. One asset class — masters, plates, cut deliverables. One action pair: `asset.download` and `asset.export`. Both already exist in shape: `apps/gateway/src/modules/demo/seed.ts:54` defines `POL-009` (`asset.download`, `resource.sensitivity: ["high"]`, `condition: { hours: [8,20], deviceTrusted: true, maxRiskTier: "elevated" }`, effect `step_up`, priority 120) and `:74` defines `POL-020` (`asset.export`, `step_up`, same hours and `deviceTrusted`, but `maxRiskTier: "low"` and a subject restricted to `["manager","admin"]`, with no sensitivity filter — so today export is both stricter on risk and blind to sensitivity, which is one of the first things the pilot bundle fixes). One control: WebAuthn step-up plus a second distinct attested approver on high-sensitivity egress — the shape `POL-011` already encodes at `seed.ts:65` with `approval: { approverRole: "manager", count: 1, distinctFromRequester: true }`. These are *demo seed* rules and the seed file dies with the rest of `/v1/demo/*`; what survives is the rule grammar and these three shapes, restated as the immutable `vajra-default-v1` bundle. One artefact: a per-title **Chain-of-Custody Evidence Pack** the facility hands the studio and the studio verifies offline.

Nothing else is in the pilot. No ingest governance beyond the single registration connector, no review-and-approve workflow, no MAM replacement, no watermarking. The fixed-scope paid pilot has exactly one written success criterion: *the facility can hand the studio, on demand, a signed pack proving every egress of that one title — and the studio can verify it on an air-gapped laptop without calling us.* That criterion is not free-standing: it consumes the per-tenant chain cutover from S2, the published trust root and the `@vajra/verify` package from S5, and the step-up primitive from S3. It is the single criterion precisely because it is the one that transitively forces the rest of the plan to be real, and it should be read as the plan's critical path rather than as one deliverable among many.

### 1.5 The honest competitive frame

Nobody in this vertical sells what VAJRA sells, and the reason is that everyone else is on the data path.

**Transfer** — Signiant Media Shuttle and Jet, IBM Aspera Faspex. They move the bytes and log the transfer. They know a file left; they do not know who was at the keyboard or who authorised it, and their logs are theirs, not portable evidence. We sit in front of them and receipt their transfers. We integrate; we never compete. Their studio-then-vendor-ecosystem motion is exactly the GTM we are copying.

**Review and share** — Frame.io, MediaSilo, Sohonet ClearView, Moxion. Session watermarking and share links for cuts and dailies, not custody of masters, no two-person rule, no verifiable receipt.

**MAM and storage** — Iconik, Dalet, LucidLink, Wasabi, Backblaze. They hold assets and have ACLs. An ACL is not evidence, and none of them can produce something a third party verifies offline.

**Forensic watermarking** — NexGuard (Nagra), Irdeto, Verimatrix. This is the best *partner* in the list, not a competitor. Watermarking answers *which copy* leaked. VAJRA answers *who held it, on what attested device, under which named policy version, and who approved.* Bind the watermark payload ID into the Proof-of-Action body and a leak investigation closes in one artefact instead of two.

**Assessment services** — Convergent Risks, Vision Media, Fortium. They audit against MPA/TPN and write findings. We are the instrument that closes three of their recurring findings continuously, which makes them a referral channel.

**IAM and PAM** — Okta, CyberArk, Delinea. Privileged-session recording and approvals exist; the output is a vendor-locked session log, and none of them understands a title, a shot, or an asset lineage.

**DLP** — Netskope, Zscaler, Microsoft Purview. Block-or-allow at the edge, with no notion of custody chain or portable proof.

Differentiation in one sentence: **everyone logs; only VAJRA emits a receipt that survives the vendor, the deployment and the key rotation, verifiable by a party who does not trust us.** That sentence describes the product being built, not the code as it stands today — see §1.6, where the gap is named exactly. The weaknesses, stated before a buyer finds them: we do not stop a phone camera pointed at a monitor, we are not a watermark, and if an asset never passes our gate we have nothing to say about it. A buyer who discovers a limitation themselves stops believing the rest.

### 1.6 Why this repo is an unusually strong starting point — and where it genuinely is not

23,363 lines of TypeScript and TSX across a pnpm workspace, with several hard parts already correct. The temptation is to claim the remaining work is merely *topological* — moving correct code under a tenant key. That is true of most of it and false of three things, and the plan is only credible if the three are named.

**Correct today.** The **audit chain construction** in `apps/gateway/src/modules/audit/service.ts:36-37` is right: `payloadHash = hashJson(payload)`, `chainHash = sha256Hex(prevHash + payloadHash)`, with a replay verifier at `:102-116` that returns `brokenAtSeq` — the first sequence number that fails. It needs to become per-tenant and versioned; the cryptography does not change. The **eight-step revocation cascade** in `apps/gateway/src/modules/identity/revocation.ts` runs credential revoke, session-version bump, device untrust, grant revoke, two-sided approval cancellation, live content-URL expiry, trust zeroing, and audit-plus-anchor in one transaction with per-step counts (`credential_revoked` … `identity_trust_zeroed`, then `appendAudit` and `enqueueLedger` `DIDRegistry/RevokeDID` at `:56-61`). That is better than most commercial IAM products expose. **Risk fails closed**: `apps/gateway/src/modules/risk/service.ts:104` returns `{ score: 100, tier: "high", signals: ["risk_service_unavailable"] }` when the remote service errors or times out, and `apps/gateway/src/modules/access/service.ts:65` independently forces tier `high` when the health snapshot says risk is down. Note the first path only exists under `RISK_MODE=http` — `:88` returns early for the `local` default — so the drill that proves it has to run the http driver.

**Correct in shape, wrong in default.** `REQUIRED_DEPS` in `packages/policy/src/index.ts:69-74` grades dependency loss by action class — `low: ["db"]`, `medium` adding `risk`, `high` and `critical` adding `ledger` — so an anchoring outage stops a sensitive export while a metadata view keeps working. That grading is the good idea. The gate that reads it is not: `:164` tests `input.health[dep] !== false` over a field typed `Partial<Record<Dependency, boolean>>` at `:89`, so a *missing* health key passes. Today's only caller returns a total record (`apps/gateway/src/modules/health/service.ts:80-83`), so behaviour is currently correct by accident of the call site rather than by construction. Inverting to `=== true` over a total `Record` is a one-line change with a regression test, and it belongs in the plan as a named fix rather than as a boast.

**The three things that are new builds, not moves.** *First*, third-party offline verification does not exist. `apps/gateway/src/modules/proof/service.ts` does push exactly five independently reported checks — `hash` (`:124`), `signature` (`:126`), `chain` (`:134`), `ledger` (`:149`), `policy` (`:173`), with `valid = checks.every(c => c.ok)` at `:175` — and that is the correct artefact shape. But it runs only as `POST /v1/verify/proof` (`apps/gateway/src/routes/index.ts:337`), against `ctx.keys.publicKey` held in the live process, with the chain, ledger and policy checks reading the database. There is no `@vajra/verify` package; `packages/` contains `contracts`, `policy`, `trust`, `chain-logic` and nothing else. Worse for the moat, `:125` ANDs signature verification and issuer equality into one boolean — `ed25519.verify(...) && body.issuer === ctx.keys.issuerDid` — so a valid signature under a retired issuer alias reports "signature bad", which is the wrong diagnosis handed to an auditor. Splitting those, adding a `kid`, publishing the trust root and shipping a zero-dependency verifier is the moat and it is unbuilt. *Second*, tenancy: a grep for `tenant`, `organization`, `org_id` or `orgId` across `apps/gateway/src` and `packages/` returns nothing. All 24 tables in `apps/gateway/src/db/schema.ts` are single-tenant by construction; that is every table, not a topology tweak. *Third*, the identity primitive changes outright — the current path is DID plus browser-held keys plus a client-trusted face match, and it is replaced, not adapted.

**The seams are real and that is what makes the rest cheap.** `DbHandle` (`apps/gateway/src/db/client.ts:10`), `StorageDriver` (`apps/gateway/src/modules/vault/storage.ts:11`) and `LedgerDriver` are honest interfaces. One caveat on the storage seam, since it is quoted as evidence: only `FsStorage` (`:31`) and `MemoryStorage` (`:66`) compute the address locally as `cidV1Raw(digestOf(ciphertext))`. The IPFS driver (`:94`) returns whatever `data.Hash` the daemon sends back and Pinata (`:132`) returns `data.IpfsHash` — neither is verified locally, and Pinata's default wrapping does not yield the same raw CIDv1. Both drivers are on the kill list anyway; the seam is sound, the four-way agreement is not a claim we can make. `packages/{policy,trust,contracts}` contain no I/O — `policy` imports only `contracts` and `@vajra/trust`, `contracts` imports only `zod` — which is what makes `decide()` unit-testable, time-travel possible, and an embeddable PDP viable. And the whole thing runs on a laptop with no Docker and no WSL: `apps/gateway/src/config.ts` defaults `DB_MODE` to `pglite` (`:15`), `LEDGER_MODE` to `lite` (`:19`), `STORAGE_MODE` to `fs` (`:29`), `RISK_MODE` to `local` (`:34`). `apps/gateway/scripts/e2e.ts` builds the real app in-process with `DB_MODE: "memory"` and `STORAGE_MODE: "memory"` (`:29-31`) and drives it through `app.inject` for 56 assertions across eleven narrated scenes — Scenes 1 through 8 plus a "Scene 3b" two-person-rule scene, plus Analyst and Ledger codas at `:242` and `:251`. Thirty-five unit tests sit in `packages/{chain-logic,policy,trust}`. That harness is the thing that makes a large refactor survivable, and keeping it green is a sequencing constraint, not a nicety.

Finally, `docs/HOW-IT-IS-BUILT.md` §14 already names six gaps in writing: lite is not consensus, the KEK is an environment variable, on-device face matching trusts the client, liveness is blink and head-pose, the audit chain serialises on an advisory lock (`pg_advisory_xact_lock(4242)` at `audit/service.ts:32`), shared packages ship TypeScript source. A codebase that documents its own limits is one you can plan against.

### 1.7 The mandate risk

The largest single risk in this section is that the facility MD says *"I will pay when a studio asks me to."* If the product only sells behind a studio mandate, the sales cycle is the studio's cycle and the whole procurement-velocity argument for choosing media collapses.

The mitigation is written into the wedge rather than bolted on: **the facility-side value has to stand alone with no studio in the picture.** A facility buys VAJRA because it closes three recurring assessment findings continuously instead of with a spreadsheet, because it can answer *who moved this master* in minutes instead of a week, and because it can put a signed pack in front of any client that asks without a project. The pilot success criterion in §1.4 is deliberately phrased as *the facility can hand the studio a pack on demand* — a capability the facility owns, exercisable before any studio has heard of us. This is the first thing tested in the first three sales calls, and if all three say the mandate is required, the correct response is to reverse the sequence and sell the studio first, at a longer cycle, rather than to keep the pricing and the plan as they stand.

### 1.8 The prove-points

Eight claims the prototype must demonstrate on demand, live, without a reset. These are what the rest of this document exists to make true.

1. **Tenant isolation is enforced by the database, not by application code.** With the application-level predicate deliberately removed, tenant B reads zero of tenant A's rows, across every tenanted table, proven by a matrix test that runs in CI on both database modes.
2. **A receipt verifies without us.** A Proof-of-Action on a USB stick, the gateway powered off, verified on an air-gapped laptop by a zero-dependency open-source checker against a published key. The artefact must staple whatever those offline checks need — the anchor attestation and the chain-range evidence — because hash, signature and issuer are the only checks that can ever be self-contained. Which checks are offline and which require a live tenant is stated on the artefact, not glossed. Change one character and it fails.
3. **Tampering is detected and localised.** Alter one byte of an audit payload in Postgres; the verifier names the exact broken sequence number, and the anchor disagrees independently.
4. **Nobody moves a master alone.** A high-sensitivity egress returns step-up plus a required approval from a distinct human; the requester cannot self-approve; the receipt names both humans, both devices and their assurance levels, the policy key and version, the bundle hash and the engine version.
5. **It fails closed, graded by what is at stake.** Stop the anchoring driver: low-sensitivity views keep working, high-sensitivity export stops with a named dependency reason in the trace. Time out the risk service: the tier is forced high, never low. A dependency whose health is simply unknown is treated as down.
6. **Revocation is immediate and total.** Revoke mid-session; the eight-step cascade counts appear, and a live brokered custody checkout dies before its expiry.
7. **Key rotation does not destroy evidence.** Rotate the signing key and the tenant KEK: pre-rotation certificates still verify under the retired `kid`, every wrapped data key re-wraps, and no ciphertext byte is rewritten.
8. **It is fast where it matters and honest where it is not.** A published decision-latency SLO defended by a load test in CI, alongside a stated limit: one anchoring writer, per-tenant chain serialisation, and the throughput number that follows.

The claim we never soften is #2. If a studio's auditor cannot check our receipt with our servers switched off, nothing else in this document matters — and today that capability does not exist in the repo at all, which is why it is the first thing the plan builds rather than the last.

## 2. Multi-tenancy and the data model

### 2.1 The isolation model, and why it is not the other two

VAJRA uses **one Postgres database, one `public` schema, a `tenant_id` discriminator column, and Postgres row-level security as the backstop**. Schema-per-tenant and database-per-tenant are both rejected for the same reason: `apps/gateway/src/db/client.ts` opens PGlite as a single embedded client (`new PGlite()` at `:49` or `new PGlite(dir)` at `:53`, then `drizzle(client, { schema })` at `:55`), and PGlite is the default (`DB_MODE` defaults to `"pglite"`, `apps/gateway/src/config.ts:15`). Every pooled-connection tenancy recipe — a second database role per tenant, a `search_path` swap on checkout, pgbouncer tricks, a connection per tenant database — either does not exist on PGlite or silently leaks across the one connection it has. Transaction-local `set_config('vajra.tenant_id', $1, true)` is the *only* seam that behaves identically on PGlite, on a `pg.Pool` (`client.ts:26`, `max: 10`), and behind pgbouncer in transaction mode. That is the whole argument, and it is decisive because the laptop profile is a shipped tier, not a dev convenience.

Schema-per-tenant loses on a second count: it turns every future migration into an N-way fan-out with no atomicity, against a repo whose journal has exactly one entry (`apps/gateway/drizzle/meta/_journal.json`, tag `0000_small_blue_shield`) and therefore zero operational experience with incremental DDL. Database-per-tenant kills the studio-oversight tier, which needs cross-tenant reads by construction.

The header comment at `apps/gateway/src/routes/index.ts:3` already tells the reader that "PostgREST (optional) serves RLS-scoped reads in production." No such thing exists: a case-insensitive grep for `row level`, `current_setting`, `set_config` or `search_path` across `apps/gateway/src` and `apps/gateway/drizzle` returns nothing, and every one of the 24 tables in `0000_snapshot.json` carries `"isRLSEnabled": false`. This workstream is the first time that sentence becomes true.

**Dedicated database is a paid tier, never a fork.** `tenants.shard_dsn` (nullable) is resolved by the same `TenantDb` seam described in S3; when set, that tenant's transactions run against their own pool with the identical schema, the identical roles and the identical RLS policies, holding a single tenant row. "We require our own database" becomes a line item, not a branch.

### 2.2 Two axes: tenants and projects

`tenants` is the hard security boundary (a facility, or a studio's oversight org). `projects` is the need-to-know boundary inside it (a title/production) — not gold-plating, because per-title need-to-know is exactly what the studio contracts for and what a TPN assessment looks at.

Of the 24 tables exported from `apps/gateway/src/db/schema.ts:404-429`, **22 take `tenant_id text NOT NULL`**. The two exceptions are decisions, not omissions:

- **`users` stays globally keyed on `did`.** A `did:key` is the base58 multicodec encoding of an Ed25519 public key and is therefore globally unique by construction; scoping it per tenant would be a lie about the cryptography. Membership moves to `tenant_members(tenant_id, user_id, role, status, invited_by, joined_at)` with `PRIMARY KEY (tenant_id, user_id)`, and `users.role` (`schema.ts:18`) is dropped after backfill — role becomes per-tenant, which is what lets one freelance colorist work for two facilities. That request arrives inside the first month of any media pilot.
- **`demo_identities` (`schema.ts:395-402`) is dropped outright**, not tenanted. It stores `private_key_jwk` server-side and there is no tenancy design that makes that acceptable.

Dropping `demo_identities` and excluding `users` is what makes the number exactly 22, and it is the same 22 that S5 quotes as the isolation-matrix count. It is not a coincidence and it must not drift: adding a 25th tenanted table without updating both numbers is a defect.

`project_id text` (nullable, because tenant-level policy and tenant-level audit both exist) goes on the ten tables that carry per-title meaning: `assets`, `asset_versions`, `asset_transfers`, `grants`, `decision_log`, `approvals`, `audit_events`, `proof_certificates`, `incidents`, `evidence_packages`. On `asset_versions` it is denormalised from `assets` and held consistent by the composite foreign key below, not by convention. Membership is `project_members(project_id, user_id, role)`.

One table is *renamed rather than added*: `access_requests` becomes `decision_log` (§2.6). It already holds `trace`, `risk_signals`, `decision`, `latency_ms` and `decided_at` (`schema.ts:205-237`) — it *is* the decision feed. Introducing a second table with those columns would duplicate thirty fields, orphan `approvals.request_id`, and quietly make the isolation matrix 23 tables wide.

New tables introduced here: `tenants`, `projects`, `tenant_members`, `project_members`, `tenant_counters`, `tenant_chain_heads`, `subject_salts`, `legal_holds`. (`tenant_keys` and `signing_keys` are defined here but owned by S5; `sessions`, `api_clients`, `oidc_connections`, `content_tokens` by S3.) All of them are tenant-scoped and all of them get RLS on the same terms as the 22 — `tenants` itself on `id = current_setting(...)`.

### 2.3 Structural integrity: the foreign keys that do not exist

Verified programmatically against `apps/gateway/drizzle/meta/0000_snapshot.json`: **24 tables, 0 foreign keys, 0 composite primary keys, 7 unique constraints, 13 indexes.** Referential integrity today is pure TypeScript convention — `devices.user_id` (`schema.ts:40`), `assetVersions.assetId` (`schema.ts:157`) and `approvals.requestId` (`schema.ts:242`) are all bare `text` columns.

That is what makes adding `tenant_id` mechanically cheap, and it is also why nothing in the database would ever catch a child row attributed to the wrong tenant. So the same migration adds `UNIQUE(tenant_id, id)` on every table that *has* an `id` column, then composite foreign keys on every parent/child edge that currently exists only in the type system:

```sql
ALTER TABLE asset_versions
  ADD CONSTRAINT asset_versions_asset_fk
  FOREIGN KEY (tenant_id, asset_id) REFERENCES assets (tenant_id, id)
  ON DELETE RESTRICT;
```

Three tables have no `id` column and take a widened primary key instead of a companion unique: `liveness_nonces` (PK `nonce`, `schema.ts:67`) → `PRIMARY KEY (tenant_id, nonce)`; `ledger_blocks` (PK `number`, `schema.ts:360`) → `PRIMARY KEY (tenant_id, number)`; `ledger_state` (PK `key`, `schema.ts:372`) → `PRIMARY KEY (tenant_id, key)`. The last one is not cosmetic: `lite.ts:34-40` upserts with `onConflictDoUpdate({ target: ledgerState.key })`, and an `ON CONFLICT` whose arbiter no longer matches a unique index throws at runtime, not at compile time. The target widens to `(tenantId, key)` in the same commit or the ledger writer breaks on the first insert.

The same composite shape covers `asset_transfers→assets`, `grants→assets`, `decision_log→assets`/`policy_versions`, `proof_certificates→audit_events`, `evidence_packages→incidents`, `policy_versions→policies`, `ledger_state_history→ledger_state`. **All `ON DELETE RESTRICT`, never CASCADE** — these are evidence tables, and a cascading delete is itself an audit finding.

Edges that point at a *person* cannot use this shape, because `users` is deliberately global. `devices`, `credentials`, `liveness_attestations`, `grants`, `decision_log` and `break_glass_grants` therefore reference **`tenant_members (tenant_id, user_id)`**, not `users(id)`. This is strictly stronger than a bare FK to `users`: it makes "this device row belongs to a person who is a member of this tenant" a database invariant rather than a code path, and revoking a membership becomes a `RESTRICT` that forces the offboarding flow in S3 to run rather than leaving orphans.

One edge pays a tax. `approvals→decision_log` crosses into a partitioned table (§2.6), and Postgres requires a unique key on a partitioned table to contain every partition-key column. So `decision_log`'s key is `(tenant_id, decided_at, id)` and `approvals` carries a `decision_decided_at timestamptz` alongside `request_id` to complete the reference. One denormalised timestamp is cheaper than the alternative, which is dropping the constraint on the one edge that governs the two-person rule.

### 2.4 The seven unique keys that break, resolved individually

The 7 table-level uniques are `users.did` (`:16`), `assets.asset_uid` (`:136`), `policies.key` (`:109`), `proof_certificates.cert_id` (`:298`), `incidents.incident_id` (`:310`), `evidence_packages.package_id` (`:328`), `demo_identities.user_id` (`:397`); plus the unique index `policy_versions(key, version)` (`:129`).

| Key | Resolution |
|---|---|
| `users.did` | unchanged — globally unique by cryptographic construction |
| `assets.asset_uid` | `UNIQUE(tenant_id, asset_uid)`, and `makeAssetUid` (`apps/gateway/src/modules/vault/service.ts:25-33`) widens `randomHex(2)` → `randomHex(5)`; two random bytes is 65,536 values per 22-char name slug, and VFX filenames repeat by convention, so `SHOT-0100-COMP` collides after a few hundred uploads inside *one* facility — today with no retry and therefore a 500 |
| `policies.key` | `UNIQUE(tenant_id, key)` |
| `policy_versions` | `UNIQUE(tenant_id, key, version)` |
| `incidents.incident_id`, `proof_certificates.cert_id`, `evidence_packages.package_id` | primary identity becomes a random ULID; the human-readable form (`INC-2042`, `PoA-20260901-000007`) becomes a display column with `UNIQUE(tenant_id, display_id)` |
| `demo_identities.user_id` | table dropped |

The display ids stop being derived from an unscoped `COUNT(*)`. `apps/gateway/src/modules/incident/service.ts:84-85` counts every incident then mints `INC-${2041 + n + 1}`; `proof/service.ts:45-50` counts every certificate (`:46`) and mints `PoA-${ymd}-${pad(n+1, 6)}` (`:49`). `proof/service.ts:197-198` is worse than the other two: `EVP-${incidentId}-${nnn}` *looks* per-incident, but the counter is a global `count(*)` over all `evidence_packages` run on `ctx.db` outside the writing transaction — so the third pack for incident 2042 can be numbered `EVP-INC-2042-017`, and the three-digit pad silently overflows.

All three are tenant-blind — facility B's first incident is numbered by facility A's volume, which leaks activity — and all three are *already* racy inside one tenant: two concurrent decisions compute the same `PoA-…-000007`, the unique violation aborts the insert, and because `buildProof` is called with the transaction handle on the allow path (`access/service.ts:273`) that rolls a legitimate access grant back into a 500. Replaced by:

```sql
INSERT INTO tenant_counters (tenant_id, kind, n) VALUES ($1, 'cert', 1)
ON CONFLICT (tenant_id, kind) DO UPDATE SET n = tenant_counters.n + 1
RETURNING n;
```

Atomic, tenant-scoped, no scan, gapless under rollback because it is a row and not a sequence. Kinds: `audit_seq`, `block`, `incident`, `cert`, `evidence`.

All 13 index definitions in `apps/gateway/drizzle/0000_small_blue_shield.sql:340-352` (4 unique, 9 plain) are rebuilt tenant-first: not one currently leads with a discriminator. `asset_versions_sha` becomes `(tenant_id, sha256_plain)`, which is what closes the cross-tenant confirm-by-hash oracle — `vault/service.ts:55` performs an unscoped lookup on `sha256Plain` and `:59` throws a 409 whose details carry another owner's `assetUid`, `name`, `version`, `ownerDid`, `sensitivity` and `sha256`.

### 2.5 RLS strategy

For each tenanted table:

```sql
ALTER TABLE assets ENABLE ROW LEVEL SECURITY;
ALTER TABLE assets FORCE  ROW LEVEL SECURITY;
CREATE POLICY assets_tenant ON assets
  USING      (tenant_id = current_setting('vajra.tenant_id', true))
  WITH CHECK (tenant_id = current_setting('vajra.tenant_id', true));
```

`FORCE` matters, but **`FORCE` is not sufficient, and believing it is would ship the laptop tier with RLS silently inert.** `FORCE` subjects the table *owner* to the policy; it does nothing to a superuser or a `BYPASSRLS` role. PGlite authenticates as the `postgres` superuser — verified on the pinned `@electric-sql/pglite@0.2.17`: with `ENABLE` + `FORCE` + policy all applied and no GUC set, `select * from t` as `postgres` returned every row of every tenant. The fix is one statement and it is load-bearing: create `vajra_app` as `NOLOGIN NOBYPASSRLS`, `GRANT` it the table privileges, and **`SET ROLE vajra_app` once at boot on the embedded connection**, after migrations and before the first request. Re-run under that role, the same three cases behave exactly as on server Postgres: no GUC returns zero rows, `GUC = 'A'` returns only A's rows, and inserting B's `tenant_id` raises *new row violates row-level security policy*. On the `postgres` driver the same split is expressed as two connection strings — a migration owner and `vajra_app` — and nothing may ever issue `RESET ROLE`.

`current_setting(..., true)` returns NULL when unset, and NULL never equals a `tenant_id`, so an unscoped connection reads nothing rather than everything — fail-closed by construction.

RLS is the *backstop*, not the control. The request-scoped `TenantDb` that opens the transaction and sets the GUC — and that makes the raw `ctx.db` handle on `AppContext` (`apps/gateway/src/context.ts:17-28`, one shared `db: Db` at `:19`) type-unreachable inside a route handler — is S3's.

### 2.6 Per-tenant audit chains, and the row lock that replaces the global mutex

`apps/gateway/src/modules/audit/service.ts:32` takes `pg_advisory_xact_lock(4242)` — one process-wide mutex held for the duration of every mutating transaction — then reads the chain head with `ORDER BY seq DESC LIMIT 1` over the whole table (`:33`) and computes `chainHash = sha256Hex(prevHash + payloadHash)` (`:37`) over a global `bigserial seq` (`schema.ts:273`). `apps/gateway/src/modules/ledger/lite.ts:56` repeats the pattern with constant `4343`, allocating `number = (last?.number ?? 0) + 1` (`:57-58`).

Replaced by a **row lock on `tenant_chain_heads(tenant_id, chain_version, tenant_seq, chain_hash, updated_at)`**, one row per tenant, taken `FOR UPDATE` inside the writing transaction — **immediately before the append, not as the first statement**. Ordering is the point: the lock serialises every chained write for that tenant, so it must cover the hash-and-insert and nothing else. Taking it first, as the advisory lock effectively does today, extends the serialised window across policy evaluation, storage I/O and every read the handler performs. There is exactly one such row per transaction, so lock-ordering deadlock is not reachable.

This is also strictly better than moving to `pg_advisory_xact_lock(4242, hashtext(tenant_id))`: the two-int advisory form occupies a *different lock namespace* from the one-int form, so during any rolling deploy old and new code would not exclude each other — on the one subsystem whose corruption is unrecoverable. A row lock has no namespace, is released at transaction end, is visible to an operator in `pg_locks`, and it eliminates the `ORDER BY seq DESC` head read at the same time, because the head hash and the next sequence live in the row you already locked. `ledger_blocks.number` is allocated the same way, from `tenant_counters` kind `block`.

`tenant_seq` comes from that locked row rather than from `bigserial`, and that fixes a live bug as a side effect. `verifyAuditChain` (`audit/service.ts:102-117`) starts a partial verification by reading `eq(auditEvents.seq, fromSeq - 1)` at `:103`; a `bigserial` is non-transactional, so a rolled-back append leaves a gap, that lookup returns nothing, `prev` falls back to `GENESIS_HASH`, and a perfectly intact chain is reported broken. A counter row allocated inside the transaction cannot gap.

The chain is **versioned, never rehashed.** Existing rows keep `chain_version = 1`, their global `seq`, and verify forever under v1 rules; `verifyAuditChain` dispatches on the column and refuses to span versions in one pass. Because every pre-cutover row backfills into `t_default`, the v1 segment is by construction single-tenant, which is what makes the frozen v1 verifier correct without a tenant predicate. Every tenant then gets a v2 genesis whose `prev_hash` **is** its v1 head's `chain_hash`, with `tenant_seq` and `UNIQUE(tenant_id, chain_version, tenant_seq)`, plus one signed crossover record stating `(tenant, v1 head seq, v1 head hash, v2 genesis tenant_seq)` so a third party can bridge the versions offline. For v1 rows `tenant_id` is a column *outside* the hashed payload constructed at `audit/service.ts:35` — putting it inside would invalidate every stored `chain_hash` and every Ed25519 Proof-of-Action signature.

**The evidence chain is split from the decision feed.** `access_requests` is renamed `decision_log`, append-only, monthly-partitioned by `decided_at`, unchained; only evidence-class facts enter the per-tenant chain. Partitions are created by the same runner that applies migrations, with a `DEFAULT` partition so an unattended laptop never fails an insert. A hash chain is inherently serial, and the honest ceiling is one chained append at a time per tenant — that is what makes the split necessary rather than tidy, and S6 owns measuring it. `audit_events` ships `chain_version` and a nullable `batch_id` from day one, unused, so Merkle batching of chain leaves can land later without a second signature-invalidating cutover.

### 2.7 Ledger namespacing

`packages/chain-logic/src/index.ts:40-46` mints flat global world-state keys — `did:${did}`, `asset:${uid}`, `policy:${id}:${version}`, `audit:${eventId}`, `incident:${incidentId}` — backed by `ledger_state` keyed on `key` alone (`schema.ts:372`) and written with `onConflictDoUpdate({ target: ledgerState.key })` (`lite.ts:34-40`), with `ledger_state_history` appended at `:41`. Two tenants minting the same `asset_uid` silently overwrite each other's on-chain record, last writer wins, and the history table records it as a legitimate update.

Every key gains a tenant segment: `t:${tenantId}:asset:${uid}`. This is a larger change than the key builder, and the plan must budget it as such: `ledger_outbox` has no tenant column, `enqueueLedger` (`modules/ledger/outbox.ts:22-27`) accepts only `{contract, fn, args, refTable, refId}`, and `LedgerDriver.submit(contract, fn, args)` has nowhere to put a tenant. So `tenant_id` becomes a first-class column on `ledger_outbox` and a first-class parameter on the driver interface, threaded through every `enqueueLedger` call site — including `audit/service.ts:52-59` and `vault/service.ts:130-137`. Per spine decision 12 Fabric is out of the plan, so `chaincode/vajra-cc` is not a coordination partner; `@vajra/chain-logic` keeps its written-once-executed-twice property and the `LedgerDriver` seam, and the key change lands **in the same commit** as the chain-version cutover, never separately.

### 2.8 Erasure and retention as schema

The three-tier model must be in the schema from the first migration because it changes what enters the hashed payload and cannot be retrofitted after pilot data exists.

- **Tier C** — `payload_hash`, `prev_hash`, `chain_hash`, `tenant_seq`. Never deleted, never rewritten.
- **Tier B** — filenames, `sha256_plain`, actor identifiers. The distinction the schema must draw is between the *column*, which stays cleartext because dedup and lineage read it, and the *commitment*, which is what enters the hashed audit payload and the ledger: `HMAC-SHA256(subject_salt, value)`, with salts in a shreddable side table `subject_salts(tenant_id, subject_kind, subject_id, salt, destroyed_at)`. Today `vault/service.ts:133` anchors raw `sha256Plain` on the ledger and `:144` writes the raw filename and hash into the audit payload — a permanent confirm-by-hash oracle over a document you may later be required to erase.
- **Tier A** — ciphertext blobs and `asset_versions.dek_wrapped` / `iv` (`schema.ts:163-164`).

Erasure nulls the Tier B cleartext columns, destroys the salt, tombstones the wrapped DEK and deletes the blob; the chain still verifies byte-for-byte, because `verifyAuditChain` recomputes `hashJson(r.payload)` from a payload that only ever held commitments. `legal_holds(id, tenant_id, project_id, asset_id, actor_did, matter_id, from_ts, to_ts, created_by, created_at, released_at)` hard-blocks the shred job. `retention_class` and `retain_until` land on `assets`, `audit_events` and `evidence_packages` with an immutable floor on evidence rows. `tenants.region` pins the database, the bucket and the KMS key — instantiated per region from the tenant row, never from global config. Grep confirms zero occurrences of `retention`, `legal hold` or `residency` in source today, and `assets.deleted_at` (`schema.ts:150`) is written in one place (`access/service.ts:258`) and read in exactly two (`provenance/service.ts:18`, `routes/index.ts:70`).

### 2.9 Migration path

Five numbered migrations, expand/contract, executed by `db:migrate` (see S6) rather than the current unconditional `migrate(db, { migrationsFolder })` at `client.ts:28` and `:56`. Only 0001 and part of 0003 are drizzle-kit output; `drizzle-orm@0.36` gives us `pgPolicy`/`pgRole` for the policy DDL, but role attributes, DML backfill and anything requiring a signature are hand-written.

- **0001 (expand, generated)** — create `tenants`, `projects`, `tenant_members`, `project_members`, `tenant_counters`, `tenant_chain_heads`, `subject_salts`, `legal_holds`, `tenant_keys`, `signing_keys`, `sessions`, `api_clients`, `oidc_connections`, `content_tokens`; rename `access_requests` → `decision_log`; add nullable `tenant_id` / `project_id` everywhere and to `ledger_outbox`; add `chain_version`, `tenant_seq`, `batch_id` to `audit_events`; add `kek_id`, `wrap_alg` to `asset_versions`.
- **0002 (backfill, hand-written DML)** — one `t_default` tenant and one `p_default` project; every existing row updated; `tenant_members` populated from `users.role` through the six-role mapping; `tenant_counters` seeded from current `MAX`/`COUNT`; `tenant_chain_heads` seeded with the current global head at `chain_version = 1`.
- **0003 (constrain)** — `SET NOT NULL` via `CHECK … NOT VALID` → `VALIDATE` → `SET NOT NULL`, so no table is scanned under an `ACCESS EXCLUSIVE` lock; `UNIQUE(tenant_id, id)` or a widened PK; the composite FKs; the re-scoped uniques; `decision_log` converted to a partitioned table; all 13 indexes rebuilt tenant-first.
- **0004 (enforce)** — `vajra_app` created `NOBYPASSRLS`, grants, `ENABLE` + `FORCE ROW LEVEL SECURITY` and one policy per tenanted table.
- **0005 (contract)** — drop `demo_identities`, drop `users.role`, drop the superseded global unique constraints.

The v2 genesis and its signed crossover record are **not** a migration. They require the per-tenant signing key from S5's `KeyProvider`, and SQL cannot produce an Ed25519 signature. They are an application step — `vajra chain cutover` — that runs after 0004, is idempotent per tenant, and is itself an audited, anchored event.

### 2.10 Tenant lifecycle

**Create** — a control-plane operation writing `tenants`, a `p_default` project, a per-tenant KEK row, a per-tenant signing key, a `tenant_counters` row per kind and a `tenant_chain_heads` genesis row, all in one transaction and itself an audited event. **Suspend** — `tenants.status = 'suspended'` blocks session issuance and every mutating route while leaving reads and verification alive, because a suspended customer must still be able to verify receipts they already hold. **Export** — a streamed, signed archive of that tenant's rows plus its chain segment plus its blob manifest, which is also the input to a dedicated-database migration. **Delete** — two phases: `status = 'deleting'` with a 30-day tombstone, then a purge that respects `legal_holds` (a hold returns a documented 409 that is itself an anchored signed event) and destroys the tenant's `subject_salts` and KEK. Because every edge is `ON DELETE RESTRICT`, the purge runs a fixed reverse-topological order in one transaction — and that order is generated from the same FK graph the migration emits, so it cannot drift from the schema. Deleting a tenant never touches another tenant's rows, because every delete is `WHERE tenant_id = $1` executed under the same RLS policy as everything else.

### 2.11 Connection strategy

One `pg.Pool` per process (today `max: 10`, hardcoded at `client.ts:26` — becomes configurable, with `statement_timeout` set, which is a Postgres-mode control and a no-op on single-threaded PGlite). Every request is one transaction whose first statement is `select set_config('vajra.tenant_id', $1, true)`; transaction-local means the GUC is discarded at commit or rollback and cannot survive on a returned pooled connection, which is also what makes pgbouncer in transaction mode safe. Because a request now holds a connection for its whole transaction, `max` and the request timeout are a single sizing decision, not two — S6 owns the number. On PGlite the identical statement runs on the single embedded connection, under `SET ROLE vajra_app`, where serialisation is a safety property rather than a limit. Tenants with `shard_dsn` set resolve to their own lazily-created pool, keyed by DSN, inside the same `createDb` seam.

### 2.12 How isolation is proved

The shipped artefact of this workstream is not a diagram, it is a test — and it is **generated from the schema export, not hand-listed**, so a new tenanted table is covered the day it is added and a table that loses its policy fails the build. For **each of the 22 tenanted tables** (plus every tenant-scoped control table from §2.2), the suite opens two transactions under two tenant GUCs, writes a row as tenant A, then issues a deliberately tenant-blind `SELECT * FROM <table>` as tenant B and asserts zero rows — plus the mirror case, a `WITH CHECK` violation when B tries to insert a row carrying A's `tenant_id`, and a third case with no GUC set at all asserting zero rows and a failed insert.

It runs on `DB_MODE=memory` *and* against a real Postgres service container in CI. On PGlite it runs under `SET ROLE vajra_app`, and the suite asserts `current_user = 'vajra_app'` as its first act — because the empirical result in §2.5 is that the same schema, the same policies and `FORCE` all pass vacuously as `postgres`, and a security test that cannot fail is worse than no test.

The tenant-blind query is a permanent test fixture, not a commented-out line in a service function: a `rawUnscoped()` helper that exists only in the test build, so the negative control is exercised on every commit rather than during a demo. That test lands in the same commit as the `tenant_id` column, never afterwards, and its output is what gets pasted into a security questionnaire.

## 3. Enterprise identity and access

### 3.1 The account is not the key

The deepest structural mismatch in the current build is that a `did:key` **is** the account. `apps/web/src/lib/did.ts:134` generates the Ed25519 pair with `crypto.subtle.generateKey({name:"Ed25519"}, false, …)` — non-extractable, stored as a `CryptoKey` in IndexedDB. `completeOnboarding` looks the user up by that DID (`apps/gateway/src/modules/identity/onboarding.ts:42`), and finding none inserts a `users` row (`:47-58`) with a role defaulted to `engineer` (`:45`) and `identityTrust: 60` (`:55`), then signs a session for it at `:98`. A second laptop therefore mints a second person. Clearing site data destroys an identity permanently, and every asset that DID owned points at a key nobody can sign for. That is unshippable to a facility where a colorist has a workstation, a review bay and a phone.

The fix is a separation, not a rewrite. The **account** becomes the federated identity — `users` gains the profile and provenance columns (`external_id`, `email`, names, `department`, `manager_id`, `source`: `scim` | `oidc_jit` | `invite`). The **key** becomes one row among many in `credentials`, widened to a general credential table with `kind` (`webauthn` | `did_key`), `credential_id`, `public_key`, `aaguid`, `transports`, `sign_count`, `attestation_fmt`, `last_used_at`, `revoked_at`. That widening is purely additive: `credentials` has no uniqueness constraint on `user_id` today — the one-row-per-user shape is a convention enforced only by `.limit(1)` at the read sites — so nothing has to be dropped. `users.did` stays globally unique and keyed as S2 specifies; it simply stops being the login. Per-tenant role lives in `tenant_members` (S2 owns that table), so a freelance colorist is an `operator` at one facility and an `approver` at another.

The legacy enum is mapped forward once and retired, and the map is written down before the migration runs: `engineer` → `operator`, `manager` → `approver`, `auditor` → `auditor`, `admin` → `tenant-admin`. No existing row is auto-granted `security-admin`; that grant is made by name, once, per tenant, because the whole point of §3.8 is that the two halves of `admin` stop travelling together. `requireRole` (`apps/gateway/src/modules/identity/session.ts:63-66`) reads the global `session.user.role`; it is replaced entirely (§3.4).

### 3.2 OIDC and SCIM

Sign-in becomes OIDC Authorization Code + PKCE at `POST /v1/auth/oidc/start` and `/callback`, driven by a per-tenant `oidc_connections` row (issuer, client id, client-secret reference, claim map, allowed email domains, group→role map). **Microsoft Entra ID is certified end to end; Okta is best-effort on the same code path.** The scope claim is not an estimate in weeks — it is that both IdPs drive one implementation and only one gets a written certification matrix (group PATCH semantics, soft-delete, nested groups, `active` toggling) exercised against a live tenant before the pilot. The trigger to certify Okta as well: two of the first five qualified facilities run it.

Provisioning is SCIM 2.0 at `/scim/v2/Users` and `/scim/v2/Groups`. Its bearer token is **not a new credential type** — it is an `api_clients` row (§3.6) scoped to `scim.*`, which means §3.6 lands with or before SCIM rather than after it, or the product ships two parallel machine-credential systems.

The deprovisioning wiring needs one correction that the obvious design gets wrong. `revokeIdentity` (`apps/gateway/src/modules/identity/revocation.ts:116-159`) is the strongest thing in the repo: eight ordered steps in one transaction — credentials revoked (`:121`), `sessionVersion` incremented (`:124`), every device untrusted via `bumpDeviceTrust(d,"owner_revoked")` (`:128`), grants revoked (`:131`), pending approvals cancelled on both the requester and approver side (`:134-138`), live content URLs expired with `expiresAt: now, contentUsed: true` (`:141-145`), identity trust zeroed (`:148`), then an `identity.revoked` audit event plus a `DIDRegistry.RevokeDID` enqueue (`:151-156`) — returning a per-step count summary. It is better than what most commercial IGA products expose. It is also **terminal and has no inverse anywhere in the codebase**. SCIM `active: false` is routinely reversible — a contractor between engagements, a leave of absence, an IdP hiccup — so wiring it to `revokeIdentity` makes a one-click, unrecoverable mistake available to any HR system. `active: false` maps to **suspend** (§3.8). SCIM `DELETE`, or an explicit per-connection deprovision policy, maps to **offboard → revoke**, and that path calls `revokeIdentity` verbatim rather than reimplementing it. Every terminal path — SCIM delete, Admin console, offboarding — funnels into that one function.

Public self-registration dies here. `POST /v1/onboard/start` and `/v1/onboard/complete` are unauthenticated (`apps/gateway/src/routes/index.ts:95,97`), and the enrolment page (`apps/web/src/app/[locale]/app/onboard/page.tsx:21,59`) posts a client-chosen `role` that `onboarding.ts:45` honours whenever `DEMO_MODE` is on — beside a panel of one-click sign-in buttons for all four roles including `admin`. Enrolment becomes invite-bound: a tenant admin or SCIM creates the member, a signed single-use invite token bound to `(tenant_id, user_id)` is issued, and `POST /v1/enrol/complete` accepts a WebAuthn registration only against a valid invite. Role comes from the invite or the group map, never from the request body. A useful side effect: the anonymous nonce mint disappears with it (§3.9).

### 3.3 WebAuthn, and the honest fate of liveness

Step-up is the product's core claim and today it is provably client-optional. `apps/web/src/components/LivenessCapture.tsx` falls through to `runSimulated` on an env flag (`:177`), on model-load failure (`:183`), on `getUserMedia` rejection (`:193`), and on two timeout paths (`:216`, `:273`) — and `runSimulated` ends by calling `finish("simulated")` at `:144`, which only signs the nonce. The server accepts `livenessMode: "simulated"` as a first-class contract value and **no server code anywhere branches on it**: `attestation.ts` records the mode beside the signature (its own docstring at `:20-27` calls it "a claim the attesting device makes about its own check"), and `packages/policy` and `packages/trust` never read it. An auditor strikes the entire step-up narrative on that one fact.

WebAuthn replaces the signature primitive with a server-checkable one. The existing nonce ceremony in `apps/gateway/src/modules/identity/nonces.ts` maps 1:1 onto a WebAuthn challenge and is kept: a 24-byte token (`:74`), a 2-minute TTL (`:64`), seven purposes (`:63`), bound to a `refId`, and deleted before validation (`:85`) so it is genuinely single-use whatever the outcome. One gap is closed while it is open: `consumeNonce` validates purpose, `refId` and expiry but never compares `row.userId` to the caller (`:82-90`), even though callers populate that column (`routes/index.ts:149`) — bind it.

`verifyAttestation` (`attestation.ts:29-56`) keeps its shape, including the property that a failed verification is still persisted with `verified: ok` (`:51`) so failures are evidence; only the inner check changes from `ed25519.verify(pub, nonce, signature)` to parsing `clientDataJSON` and `authenticatorData` and asserting the **UV flag**, the RP ID hash, the challenge match, and a monotonic `sign_count`. That evidence property has to be *extended*, not just preserved: the onboarding path does not have it. `onboarding.ts:40` throws `attestation_invalid` before any row is written, and both of its attestation inserts hardcode `verified: true` (`:74`, `:129`). And the swap lands at **four call sites, not two** — `stepUp` (`access/service.ts:298`), `decideApproval` (`access/service.ts:447`), identity revocation (`routes/index.ts:160`) and incident closure (`routes/index.ts:361`) — plus the enrolment path. Costing it at two understates the change by half and misses the two most sensitive actions in the system.

`assurance_level` — `hardware` | `platform` | `simulated` — is recorded on the attestation, on the session, and in the Proof-of-Action, and consumed by the PDP as a condition on the terms S4 sets. Per-tenant AAGUID allowlists let a facility require a specific authenticator model on high-sensitivity egress. `simulated` is refused outside the sandbox tenant — with the sequencing caveat that the harness sends `livenessMode: "simulated"` today (`apps/gateway/scripts/e2e.ts:162,235`), so the sandbox-tenant carve-out ships in the same commit that starts refusing it, or 56 assertions go red (§3.9).

**Liveness's honest fate: it is demoted from a control to a signal, and it stays.** The face descriptor never leaves the browser — `did.ts:187-192` matches on-device against `FACE_MATCH_THRESHOLD = 0.55` (`:177`), the server receives only mode/score/signals, `biometricsStored: 0` is asserted in `/v1/stats` (`routes/index.ts:89`) and `biometricBytesStored: 0` in the onboarding audit payload (`onboarding.ts:91`). That is a real DPDP/GDPR special-category commitment and it costs nothing to keep. What it can no longer do is satisfy a policy on its own. This has a specific operational consequence for the vertical: MPA secure-area rules commonly ban personal phones on the floor, which breaks the passkey-on-your-phone assumption. The pilot therefore attests **approvers, not artists** — facility-issued FIDO2 keys for the approver bench (20–25 at a 200–800-seat facility, a number to confirm in the first three sales calls, not to design around) rather than one per artist — because the two-person rule only needs the approver side hardware-attested. If a design partner will not fund even that, the fallback is platform authenticators on managed workstations at `assurance_level: platform`, and the policy floor for `asset.export` drops accordingly and visibly on the Assurance Board.

### 3.4 The request-scoped principal

There is no per-request context object in the codebase: `AppContext` (`apps/gateway/src/context.ts`) holds one long-lived `db` handle that all 82 exported functions under `apps/gateway/src/modules` address directly, and `apps/gateway/src` registers zero Fastify hooks. A `preHandler` — the first hook in the repo — resolves the principal and constructs `RequestContext { tenantId, projectId, principal, role, assuranceLevel, db: TenantDb }`.

What that hook must **not** do is open a request-long transaction. PGlite is a single embedded connection, so a transaction held for the life of a request serialises the entire gateway; services already open their own transactions through `withTx` (`context.ts`), which would nest into savepoints; and requests routinely perform network I/O mid-flight — the risk service at `RISK_MODE=http` with a 150 ms timeout, storage writes — which a held transaction would straddle while holding the `tenant_chain_heads` row lock that S2 makes the serialisation point. Instead, `TenantDb` wraps every statement and every transaction, issuing `select set_config('vajra.tenant_id', $1, true)` as the first statement *inside* each transaction — the only form that behaves identically on PGlite and a pooled Postgres — and `withTx` becomes the single seam every service goes through. Raw `ctx.db` is branded `UnscopedDb` and no service signature accepts it, which is what makes bypass a type error rather than a code-review question; touching 82 signatures is the mechanical cost of that guarantee and belongs in the estimate. Session claims gain `tid` and carry the per-tenant role resolved from `tenant_members` at sign-in.

`requireRole` is deleted from all 12 of its call sites in `routes/index.ts` (`:104,130,147,154,174,277,353,359,368,374,406,427`) and replaced by a single `enforce(principal, action, resource)` PEP helper. Two of those call sites are not simple substitutions: `identity.revoke` (`:154`) and `policy.edit` route through the PDP, which means revocation acquires step-up plus a second distinct approver and a signed receipt instead of today's bare `admin` string test. The same change removes the quiet super-power at `access/service.ts:453`, where an `admin` satisfies any approval regardless of the spec's `requiredRole`.

While in `session.ts`: the `dev` claim is documented as "device fingerprint hash" (`:17`) and `signSession`'s parameter is named `deviceFingerprintHash` (`:30`), but every caller passes `device.id` (`onboarding.ts:98,135`; `routes/index.ts:105,467`) and `verifySession` resolves it as `devices.id` (`:54`). Rename it before a tenancy refactor propagates the confusion.

### 3.5 Sessions

Today: HS256 over a shared `SESSION_JWT_SECRET` whose default is the literal `dev-only-session-secret-change-me` (`apps/gateway/src/config.ts:42`), a 15-minute TTL (`:43`), an unbounded `POST /v1/session/refresh` that re-signs on any valid session with no absolute cap, no re-attestation and no `appendAudit` (`routes/index.ts:102-106`), no logout route among the 49 registrations, and a web client that writes the bearer into a JS-readable cookie with `samesite=lax`, no `HttpOnly`, no `Secure`, `max-age=3600` (`apps/web/src/lib/api.ts:49-51,59`). Symmetric signing means verification capability equals forgery capability.

Target: EdDSA with a `kid` header and a rotating key set — drawn from a **session-signing purpose of the `KeyProvider`, never the proof key**, which today is the single pair derived from `PROOF_SIGNING_SEED` at `app.ts:38` and would otherwise be quietly reused. A `sessions` table (`id`, `tenant_id`, `user_id`, `credential_id`, `auth_method`, `assurance_level`, `created_at`, `last_seen_at`, `absolute_expiry`, `ip`, `user_agent`, `revoked_at`) with its `id` as the JWT `jti`; a 12-hour absolute lifetime and a 30-minute idle timeout independent of the 15-minute access token; refresh bound to that row and audited; `POST /v1/logout` revoking it; `DELETE /v1/me/sessions` and an admin equivalent; an admin session inventory. Crossing an assurance boundary requires a fresh attestation rather than a free refresh. The `HttpOnly` cookie is not free: the web app is a Next static export with no server to set one, so it depends on the BFF S7 introduces — until that lands the token stays in memory with a same-site refresh path, and the cookie is not called a fix before it is one.

**The `sessionVersion` comparison survives untouched.** `verifySession` re-reads the user on every request and compares `user.sessionVersion` to the token's `sv` (`session.ts:49-51`) — that per-request read is deliberate, not an inefficiency to optimise away, and it is the only instant global kill switch, exercised by both `revocation.ts:124` and the incident ladder at `incident/service.ts:151`. The `sessions` lookup joins that same read rather than adding a second round trip. So does the stale-token tolerance at `session.ts:52-53`, which accepts a stale token *only* for a revoked identity so the trace can say `identity_revoked` rather than a generic 401.

### 3.6 Service accounts

There is exactly one credential type today: the `auth` helper (`routes/index.ts:50-54`) accepts `Authorization: Bearer <session jwt>` and nothing else, and no API-key table exists among the 24. A CI job minting an Asset Passport, a MAM sync or a SIEM pull therefore has no option but to carry a human's token, which destroys the claim that every action ties to an attested person. Add `api_clients(tenant_id, name, owner_user_id, scopes[], key_hash, prefix, expires_at, last_used_at, revoked_at)`, accept `Authorization: Bearer vjr_<prefix>_<secret>` alongside session JWTs, and resolve both to a `Principal` union `{ human | service }`. Hashing is `scrypt` from `node:crypto` or a prebuilt-binary argon2id — **not** the default `argon2` package, whose node-gyp build breaks the zero-setup laptop run that is a shipped product tier. Every audit event gains `actor_type` and `actor_client_id`. Keys are action-scoped with a forced expiry.

Human-only actions are an explicit check, and it has a dependency worth naming: `DecisionInput.user` (`packages/policy/src/index.ts:81`) carries only `did`, `role`, `status`, `vcRevoked` — there is no representation of a non-human principal in the PDP input at all. `actor_type` and `assurance_level` enter `DecisionInput`, and "this action requires a human" becomes a rule in `vajra-default-v1` rather than an `if` in a handler, so the refusal is legible in the trace instead of being a 403 with no explanation.

### 3.7 Device posture

`devices.fingerprintHash` is a client-supplied string. `signInExisting` matches on `and(eq(devices.userId, user.id), eq(devices.fingerprintHash, body.deviceFingerprintHash))` taken straight from the request body (`onboarding.ts:110`), skips the new-device trust penalty on a hit (`:113-119`), and binds the session to that row — so anyone who can sign for a DID presents the known-good laptop's fingerprint from any machine and inherits its `trusted` flag, silently defeating the `deviceTrusted` policy condition. The seeded demo devices are inserted with `trusted: true` outright (`demo/seed.ts:134`) against a fingerprint that is itself a source literal, `sha256Hex('vajra-demo-device:' + role)` (`seed.ts:78-80`). The fingerprint is a SHA-256 of user agent, language, screen width/height/depth, timezone offset and core count (`did.ts:199-212`) — neither stable across a browser update nor unique across a fleet of identical facility workstations.

Device identity becomes something the server minted: the WebAuthn `credential_id` and `aaguid` are the durable anchor, with a server-issued `HttpOnly` device cookie as a correlator only — a cookie is per-browser-profile and dies with site data, which is exactly the fragility §3.1 removed from the account and must not be reintroduced as a hard dependency. The `devices` unique index is `(user_id, fingerprint_hash)` (`schema.ts:34-35`), so replacing the natural key is a migration with live rows, not a column swap.

Add `device_posture(device_id, source, managed, disk_encrypted, os_version, patch_age_days, edr_present, checked_at)` as a first-class set of policy conditions — the `devices` table has no posture column today. Populate it through an authenticated ingest endpoint keyed to an `api_clients` row, **not** through two MDM connectors: S7 budgets exactly one connector for the pilot and S8 names the second as a pre-agreed casualty, so Intune is the first posture connector *after* the pilot and Jamf follows demand. Add the admin device actions the console lacks entirely — trust, untrust, revoke, rename — each audited, reusing `bumpDeviceTrust`. Devices with no posture report inside a configurable window decay to `managed: false` rather than remaining silently trusted.

### 3.8 Delegated admin, break-glass, and offboarding

`admin` is one god role — it satisfies any approval regardless of the required role (`access/service.ts:453`) and gates eight of the twelve `requireRole` sites. Split it: `tenant-admin` (members, connectors, billing), `security-admin` (policy, keys, break-glass), `operator`, `approver`, `auditor`, `member`, enforced in `enforce()` rather than by flat enum membership.

Break-glass is scaffolded in three places and implemented in none: `break_glass_grants` exists (`schema.ts:256`) and is referenced only by the export list (`:419`) and the demo wipe loop (`seed.ts:14,89`); `PolicySpec.breakGlass` validates `{ eligibleRoles, ttlMinutes ≤ 120 default 15, approverRole }` (`packages/contracts/src/index.ts:141-147`) and is never read by the PDP; the `break_glass` nonce purpose has no caller. Either implement or delete — a schema for a feature that does not run is worse than no feature. Implement to the shape the contract already declares: `POST /v1/break-glass/request` → an approver of the spec's `approverRole` decides with a WebAuthn attestation → a grant row bounded by `ttlMinutes` → an incident opened for the window → every action inside it flagged in its Proof-of-Action with a dedicated `break_glass` trace check. One detail decides whether that works: this codebase's severity ladder runs the *other* way from the convention — `S1` forces step-up, `S3` locks the session, expires content URLs and revokes temporary grants (`incident/service.ts:143-145`). Opening the "most severe" incident alongside a break-glass grant would freeze the exact actions break-glass exists to permit. It opens an `S1` plus a typed `break_glass` marker, and the ladder is not driven from it.

The ordinary `grants` table is in worse shape than a label — it is a dead branch on both ends. No code path anywhere inserts a grant row (`insert(grants)` has zero occurrences); the table is only ever revoked from (`revocation.ts:131`, `incident/service.ts:158`) or read for derivative status (`vault/service.ts:77-84`). And `DecisionInput.hasGrant` exists (`policy/index.ts:91`) and is read by the ownership check (`:219`), but the single `decide()` call site (`access/service.ts:72-83`) never populates it. Delegation therefore needs two changes, not one: a grant-issuing path, and the field actually passed.

**Operator break-glass is a separate, harder problem and the current build makes it unrecoverable.** No route writes `users.role` at all — the only `update(users)` statements set status and `sessionVersion` (`revocation.ts:124`, `incident/service.ts:151`) and identity trust (`trust/service.ts:23`) — and `POST /v1/identities/:did/revoke` blocks self-revocation with `cannot_revoke_self` (`routes/index.ts:159`), so with `DEMO_MODE` off a facility whose only admin loses their authenticator is locked out permanently. The cheap fix comes first and makes the expensive one rare: a **last-admin invariant** — a tenant is provisioned with at least two `tenant-admin` members and no operation may remove or suspend the last one. Behind it sits an offline-signed, tenant-scoped, single-use recovery token that can only mint a time-boxed recovery `tenant-admin`, always opens an incident, always notifies the tenant's other admins, and is itself anchored. Its signing root is **tenant-held**, escrowed at provisioning; a vendor-held co-signing key is an option the tenant can decline at install, because "we can mint an admin inside your tenant" is not a sentence that survives a facility's own security review of the single-box topology. The notification leg depends on the event bus S7 sequences, so the token ships with email as its floor and Slack/Teams when that lands. Key recovery for an ordinary user is simpler: a passkey is one credential of several, so losing one means an admin revokes it and issues a fresh enrolment invite — the account, its history and its owned assets untouched.

Offboarding is a distinct lifecycle step, not a synonym for revoke. Today revocation is a one-way door with no inverse and no ownership transfer: `assets.ownerDid` keeps pointing at a dead DID and the custody chain forks if the person returns. Split into **suspend** (reversible; `status: 'suspended'` — a value `USER_STATUSES` carries (`contracts/src/index.ts:13`) and the PDP already branches on (`policy/index.ts:176-177`), but which nothing in the repo can currently set, since the only writer of `users.status` is `revocation.ts:124` — plus a `sessionVersion` bump and frozen grants), **offboard** (ownership reassigned to a named successor or a facility custody account as a first-class `asset_transfers` row with `reason: 'offboarding'`, so provenance stays continuous), and **revoke** (cryptographic, terminal, `revokeIdentity` unchanged). SCIM `active:false` drives the first; SCIM delete drives the last two in order; the Admin console drives all three.

### 3.9 Sequencing, and what is deleted

`packages/dev-idp` — a small in-process OIDC provider mounted only under the laptop profile, issuing real Authorization Code + PKCE tokens for seeded sandbox users, alongside a scripted WebAuthn authenticator for the harness — **lands and turns the 35 unit tests and 56 e2e assertions green in an earlier commit than the one that deletes `/v1/demo/*`.** This is not stylistic, and the coupling is deeper than one route. The harness depends on the demo surface in four distinct ways: it authenticates exclusively through `POST /v1/demo/login` (`gateway.test.ts:37`; `e2e.ts:91-94,195,237`, with `DEMO_MODE: "true"` pinned at `gateway.test.ts:51` and `e2e.ts:35`); it reads seeded **private keys straight out of `demo_identities`** to produce attestation signatures (`e2e.ts:61-62`, used at `:161,234`); it uses `demo_identities.deviceFingerprintHash` as the scenario device so requests land on a trusted device (`e2e.ts:129,135`); and Scene 1 drives the unauthenticated `/v1/onboard/complete` with a self-minted keypair, including a replay assertion (`e2e.ts:74-88`). The replacement commit must therefore ship four things — an OIDC login helper, a scripted authenticator, a server-minted test device, and an invite-issuing path — and a sandbox tenant that still accepts `assurance_level: simulated` (§3.3). Deleting the demo routes first destroys the project's only verification mechanism in a single commit. The payoff is that the laptop demo then exercises the same OIDC code path as Entra rather than a bypass.

| Deleted | Why a flag cannot save it |
|---|---|
| `POST /v1/demo/login`, `/sign`, `/reset`, `/outage`, `/drain`, `GET /presets` | `requireDemo()` checks only `ctx.config.DEMO_MODE` (`routes/index.ts:436-438`), which **defaults to true** (`config.ts:48`); `/v1/demo/login` has no `auth()` call and returns a session JWT for the requested role — including `admin` — with no audit event (`:457-468`) |
| `demo_identities` and `seedDemo`'s keys | Derived as `keyPairFromSecret('vajra-demo:' + role)` (`seed.ts:123`) and stored as a private JWK (`:145`) — recomputable by anyone with the source. Turning the flag off does not close it: `/v1/onboard/complete` is unauthenticated and has no demo check, so an attacker signs the onboard nonce with the derived admin key and `signInExisting` (`onboarding.ts:107-141`) mints an admin session on any database that was ever seeded |
| Public self-registration + client-chosen role | `onboarding.ts:45` honours `body.role` under demo mode; with it off, everyone is `engineer` forever, since no code path anywhere writes `users.role`. The product's only two states are "anyone can be admin" and "nobody can" |
| Client-supplied `deviceFingerprintHash` as a trust path | A value the client chooses cannot gate a `deviceTrusted` condition |
| `livenessMode: "simulated"` outside the sandbox tenant | A control the client declines by refusing camera permission is not a control |

Two smaller repairs ride along, because the unauthenticated auth surface is currently unmetered and unrecorded. `sweepExpiredNonces` is exported from `nonces.ts:37` and has **zero callers** repo-wide, while `createNonce` inserts a row on every anonymous `/v1/onboard/start` — schedule the sweep on the outbox timer and cap outstanding nonces. Note what the per-IP form of that cap is worth on its own: `clientIp` trusts the first `x-forwarded-for` element unconditionally (`routes/index.ts:41`), so the cap is spoofable by a header until Fastify's `trustProxy` is configured against a known proxy set. The load-bearing fix is §3.2 — invite-bound enrolment deletes the anonymous mint entirely — and the cap is defence in depth behind it. Second, the audit vocabulary has no `auth.succeeded`, `auth.failed`, `session.refreshed`, `session.revoked`, `identity.role_changed` or `device.trusted`; neither `/v1/demo/login` nor `/v1/session/refresh` calls `appendAudit`, and `onboarding.ts:40` throws `attestation_invalid` without recording the failure. `appendAudit` types `eventType` as a bare `string` (`audit/service.ts:21`), so the same change introduces the typed union — otherwise the vocabulary drifts the moment it is written. Each new event carries IP, user agent, auth method, `actor_type` and `assurance_level`. These are cheap because `appendAudit` and the hash chain already exist — and without them an incident responder cannot answer "who signed in, from where, and did anyone fail," which is the first question of every breach review.

## 4. The decision engine as a product

### 4.1 The line that does not move

`decide()` in `packages/policy/src/index.ts:145` is a pure, synchronous, I/O-free function of one explicit input object. Its header comment numbers eight in-engine stages — fail-closed dependency check, identity, RBAC, explicit deny, ABAC conditions, trust gates, risk overlay, approval overlay — with the ninth, the audit append, explicitly delegated to the caller; two further overlays, the ownership check at `:216-221` and the incident overlay at `:302-317`, run unnumbered between them. It returns a `DecisionOutput` carrying a `DecisionTrace`, the reason codes, the matched `PolicyVersion`, the approval requirement and an `afterStepUp` look-ahead. That purity is not an aesthetic preference; it is load-bearing three times over. It is why `packages/policy/src/index.test.ts` holds 13 tests with no mocks and no database. It is why `apps/gateway/src/modules/audit/timetravel.ts` can reconstruct what the system believed at an arbitrary past instant by replaying event streams into `effectivePermissions()` with no snapshots (`:57`). And it is the only reason an embeddable PDP is possible at all. The function already accepts `now` as an optional input rather than reading the clock (`:146`) — that discipline extends to everything below. Nothing in this section reaches for the database, the network or the clock from inside `decide()`.

Everything else about the engine changes.

### 4.2 Splitting the PDP from the workflow

Today `decide()` has exactly one call site in the whole gateway: `apps/gateway/src/modules/access/service.ts:72`, buried inside `requestAccess`, reachable only through `POST /v1/assets/:uid/request` (`apps/gateway/src/routes/index.ts:212`), which then writes an `access_requests` row, appends to the hash chain, mints a Proof-of-Action, evaluates incidents and recomputes asset trust (`:168`). You cannot ask this system a question. Every integration a facility will want — a ShotGrid hook checking whether an artist may pull a plate, a transfer-tool pre-flight gate, a MAM plugin greying out an export button — needs an answer without producing evidence.

So: **`POST /v1/decide`** takes `{principal, action, resource, context}`, resolves trust, risk, the PolicyBundle and dependency health server-side, and returns `{verdict, actionClass, trace, decisionId, ttlMs, bundleHash, engineVersion}`. It appends nothing to the audit chain and mints no Proof-of-Action; it does write a row to the unchained, partitioned `decision_log` that S2 already provisions, because an unlogged decision oracle is its own audit finding. `ttlMs` is advisory — it tells a PEP how long to grey out a button, and is explicitly not a capability: the only thing that moves bytes is `POST /v1/authorize` followed by a custody checkout. The endpoint is rate-limited per principal for the same reason `GET /v1/policies` is being locked down in §4.5: an unmetered PDP is a ruleset-enumeration oracle. **`POST /v1/authorize`** — today's `/v1/assets/:uid/request` — is the evidence-producing PEP workflow layered on top of the same call, unchanged in behaviour. **`POST /v1/decide/simulate`** takes a candidate ruleset alongside the input and runs the real engine.

That last endpoint kills a live liability. `apps/web/src/app/[locale]/app/policies/page.tsx:37-55` contains `previewOutcome`, a nineteen-line second policy engine in the browser. It knows about `subject.role`, `resource.sensitivity`, `condition.hours`, `deviceTrusted` and `maxRiskTier`, and knows nothing about `ROLE_ACTIONS`, `resource.class`, ownership, `TRUST_GATES`, the risk overlay, the incident overlay, dependency health, or the unconditional `if (sensitive) stepUp = true` at `:320`. It prints ALLOW for a high-sensitivity download the real engine returns STEP_UP for, and prints PENDING_APPROVAL where the engine returns STEP_UP and only reaches PENDING_APPROVAL after an attestation. Its own doc comment at `:32-36` concedes the divergence. Handing a facility's security lead a pre-flight check that disagrees with the enforcement path is worse than shipping none; it is deleted and the panel repointed at `/v1/decide/simulate`.

### 4.3 The PolicyBundle

A Proof-of-Action names `POL-009 v3` and its `specHash`. An auditor reads that as *this rule produced this outcome*. It did not. The verdict is mostly produced by TypeScript literals that are unversioned, unhashed, and absent from the signed evidence:

| Constant | Location | Example value |
|---|---|---|
| `ROLE_ACTIONS` | `packages/policy/src/index.ts:35-49` | `auditor` may only `asset.view` |
| `actionClassFor` | `packages/policy/src/index.ts:51-67` | `asset.delete` / `policy.edit` / `identity.revoke` → `critical` |
| `REQUIRED_DEPS` | `packages/policy/src/index.ts:69-74` | `high` and `critical` require `db`, `risk`, `ledger` |
| `TRUST_GATES` | `packages/trust/src/index.ts:27-32` | critical: identity soft 75 / hard 60, device soft 70 / hard 50 |
| `RISK_WEIGHTS`, thresholds | `packages/trust/src/index.ts:207-218` | `new_device` 30, burst > 10, volume ratio > 3, new-user floor at 48 h |
| `tierFor` cut-points | `packages/contracts/src/index.ts:427-431` | ≥ 60 high, ≥ 30 elevated |
| forced step-up on sensitive | `packages/policy/src/index.ts:320` | `if (sensitive) stepUp = true` |
| critical-class default approver | `packages/policy/src/index.ts:327-328` | `admin` if the requester is an admin, else `manager`; count 1, distinct |
| risk fail-safe substitution | `apps/gateway/src/modules/access/service.ts:65` | risk service down ⇒ score 100, tier `high` |

Two facilities on two builds get different verdicts from a byte-identical policy, and nothing in the signed artefact reveals it. Also: the sales answer to "we need a trust floor of 90 for masters" is currently "we will fork the build for you."

Fix: a **PolicyBundle** — `{ruleset, actionClasses, roleActions, trustGates, riskWeights, riskTiers, dependencyMatrix, dependencyFallbacks, engineVersion}` — hashed with the existing `hashJson` (`apps/gateway/src/lib/crypto.ts:103`) and passed to `decide()` as a second explicit argument. Today's literals ship as the immutable bundle `vajra-default-v1`, byte-for-byte behaviour-identical, so nothing regresses on day one.

Two consequences the hoist forces, both of which are the actual work. First, `decide()` is not the only reader of those tables: `effectivePermissions()` reads `ROLE_ACTIONS` at `:374` and `TRUST_GATES` at `:380`, and it has four call sites (`access/service.ts:179`, `:371`, `:527`, `audit/timetravel.ts:57`) feeding `/v1/me`, every access response and the time-travel view. If the bundle threads only into `decide()`, `effectivePermissions()` becomes the third shadow engine — exactly the sin §4.2 deletes. Both exports take the bundle; no module-level table stays reachable from either. Second, the last row in that table lives in the gateway, not the engine: when the risk service is unreachable, the PEP substitutes a maximum score before calling `decide()`. An SDK PEP that assembles its own `DecisionInput` inherits none of that and silently scores a risk-blind request as calm. The substitution rule moves into the bundle as `dependencyFallbacks` and is applied by a `buildDecisionInput()` helper that ships with `@vajra/policy`, so the fail-safe travels with the bundle rather than with one server. The `DecisionTrace` and every Proof-of-Action then cite `bundleHash` and `engineVersion` alongside the policy reference — see §4.9 for why both are needed.

### 4.4 Conflict resolution, and the gate that fails open

`priority` defaults to 100 in `PolicySpecSchema` (`packages/contracts/src/index.ts:148`). The seven seeded specs all set it explicitly — six at 100, POL-009 at 120 (`apps/gateway/src/modules/demo/seed.ts:51-76`) — and because no two of them share an `action`, the seed never actually produces a tie. That is the trap, not the reassurance: the hazard is latent, it is invisible in every demo, and it arrives with the first customer-authored rule, because an override is by definition a second rule on the same action and an author who omits `priority` gets 100. Resolution today is `[...matching].sort((a, b) => b.spec.priority - a.spec.priority)[0]` at `packages/policy/src/index.ts:198` and again at `:205`. `Array.prototype.sort` is stable, so equal priorities preserve input order, and input order is whatever `listActivePolicyVersions` returned — `.orderBy(policyVersions.key, desc(policyVersions.version))` at `apps/gateway/src/modules/policy/store.ts:34`. A facility adds a deny rule for a title, it lands with a lexically later `POL-` key, and the allow keeps winning silently.

Resolution becomes total and safety-biased: **deny beats every other effect regardless of priority**, then `require_approval` > `step_up` > `allow`, then higher priority, then lexically smaller `(key, version)` as a documented final tiebreak. `POST /v1/policies/lint` reports shadowed, unreachable and same-priority-conflicting rules across the whole set, and `POST /v1/policies` rejects a write that introduces an overlapping same-priority conflict, naming both keys.

Separately, `packages/policy/src/index.ts:164` reads `const ok = input.health[dep] !== false` against a `DecisionInput.health` typed as `Partial<Record<Dependency, boolean>>` (`:89`). A missing key reads as healthy. In the gateway this is masked because `HealthService.depsForDecision()` (`apps/gateway/src/modules/health/service.ts:80-83`) already returns a total `Record<Dependency, boolean>` with all four keys — but the moment `decide()` runs inside an SDK or a PEP that only knows about `db`, a critical action passes the fail-closed gate with the ledger and risk service both unreachable. In a component whose headline property is *fail closed*, an absent input must never read as a pass. The check inverts to `=== true` and the input type becomes a total `Record<Dependency, boolean>` so a partial map does not compile. One extra unit test in `packages/policy/src/index.test.ts` covers the empty-health case.

Both changes in this subsection alter what the engine computes from unchanged inputs, so neither is a bundle change: they are `engineVersion` increments. `vajra-default-v1` is behaviour-identical as a *constant table*; the engine that consumes it is not frozen. That distinction is the whole reason §4.9 records both hashes, and the reason the verifier pins `engineVersion` and refuses to re-run a v1 decision under a v2 engine rather than quietly producing a different answer.

### 4.5 Whose rules apply

`GET /v1/policies` at `apps/gateway/src/routes/index.ts:270-273` is `await auth(req)` with no role check at all, returning every version ever created via `listAllPolicyVersions` — an engineer can read every deny rule in the estate. The ruleset is the most sensitive artefact in a security product: it is a map of what an organisation guards and how. `GET /v1/policies` gates behind a `policy.read` capability, and `/v1/decide` returns the matched policy reference only to principals holding it — everyone else gets the verdict and the check list without rule keys.

The engine-side half of tenancy is a discipline, not a feature: scoping happens in the query that builds `input.policies`, never inside `decide()`. That is precisely what keeps the function pure and the 13 unit tests meaningful, and it is why the tenant and project predicates on `listActivePolicyVersions` (`store.ts:29-36`) and the request-scoped `TenantDb` that carries them belong to S2 and S3 rather than here. What S4 owns is the consequence: once a facility runs an org-level baseline plus per-title overrides, two rules can match one request by design, so **project-scoped rules outrank tenant-scoped rules before the §4.4 ordering applies**, and the trace records the scope of the winning rule and the scope of every rule it beat. Without that clause, "add an override for this title" resolves through the same row-order accident §4.4 just deleted.

### 4.6 Authoring, staging, rollback, and the ruleset in the customer's git

`createPolicyVersion` (`apps/gateway/src/modules/policy/store.ts:48-95`) is genuinely good: it never edits, it closes the current version by setting `activeTo`, computes `max(version)+1` scoped to the policy, enqueues both `ClosePolicyVersion` (`:69`) and `AnchorPolicyVersion` (`:77-83`), and writes a `policy.version_created` audit event (`:84-92`) — all in one transaction. Decisions cite `policy_version_id`. That storage model stays. What is missing around it:

**Idempotency.** `specHash` is computed at `:50` and stored at `:75` but never compared against the current version's hash before writing. A nightly CI apply of an unchanged repo mints a new version of all seven policies, closes seven, enqueues fourteen ledger transactions and writes seven audit events. Within a month the version history — the artefact sold to auditors — is unreadable noise. An incoming spec whose hash equals the active version's returns the existing version with 200 and writes nothing.

**Lifecycle verbs, and the hazard under them.** `const now = new Date()` at `:58` feeds `activeFrom: now` at `:75`, so activation is always immediate — even though `isActiveAt` (`packages/policy/src/index.ts:115-120`) already implements future activation correctly. Accepting an optional `activeFrom` is a two-line change that breaks the surrounding transaction if made naively: the "current" version is found by `isNull(policyVersions.activeTo)` ordered by `desc(version)` at `:59-66`, so a future-dated version is immediately treated as current, gets closed by the next write while the genuinely live version stays open, and the ruleset then holds two simultaneously-active versions of one key — landing straight in the §4.4 tie case. Scheduled activation therefore ships *with* a rewritten predicate that selects the version live at `now`, a uniqueness constraint forbidding overlapping `[activeFrom, activeTo)` windows per key, and a test that schedules, supersedes and cancels. `POST /v1/policies/:key/rollback/:version` re-anchors a named prior spec as a new version with `rollback_of` in the audit payload. `POST /v1/policies/:key/retire` closes the version with no successor.

**Bundle apply.** `PUT /v1/policies/bundle` applies a whole ruleset in one transaction, returning created/updated/unchanged/removed counts, with `?dryRun=true` returning the diff and writing nothing. `GET /v1/policies/bundle` returns a canonical bundle signed through the `KeyProvider` seam and `kid` that S5 owns. `vajra policy plan | apply | export` wraps both, so a studio's ruleset lives in their repo, ships through their PR review with the dry-run diff posted as a comment, and a rejected plan is a failed check rather than a conversation.

**Bootstrap.** The seven policies that make this system function at all are `DEMO_POLICIES` in `apps/gateway/src/modules/demo/seed.ts:50-76` — inside the module the plan deletes. Without them a fresh tenant has zero policies and `decide()` denies everything with `no_policy` at `:193`. The default ruleset is therefore extracted into `vajra-default-v1` and provisioned to every tenant at creation as a signed bundle, in the same commit that removes the seeder; an empty ruleset becomes a loud startup error, never a silent global deny.

### 4.7 Re-deciding at finalization

`decide()` runs once, at request time. When the step-up assertion arrives up to `STEP_UP_TTL_MS` (10 minutes, `apps/gateway/src/modules/access/service.ts:29`) later, or an approver acts up to 24 hours later (`:338`), the verdict is replayed from the frozen `request.trace` (`:295`, and again at `:443` in `decideApproval`). In that window the ruleset may have tightened, the person's identity trust may have collapsed after a failed liveness attempt elsewhere, an S2 incident may have opened, or the ledger may have gone down — none of it is consulted, and the egress completes under the old world.

Worse, the approval requirement is reconstructed by reading the trace back: `String(approvalCheck.params?.role ?? "manager")` and `Number(approvalCheck.params?.count ?? 1)` at `:334-335`, both silently defaulting, before being written to `approvals.requiredRole` / `requiredCount` (`apps/gateway/src/db/schema.ts:244-245`). Those columns exist; what does not exist is a path from `decide()`'s typed `ApprovalRequirement` to them. Three things fall out of that round trip. `distinctFromRequester` is dropped entirely — `decideApproval` enforces it unconditionally at `:436`, which is the safe answer but means the field in `PolicySpecSchema` is decorative. `requiredCount` is persisted and then never read: `decideApproval` marks the approval `approved` on the first approver (`:472`), so a spec written with `count: 2`, which the schema permits up to 3, silently degrades to one-of-one. And `:437` lets any `admin` satisfy any `requiredRole`, so a rule demanding a manager is satisfiable by the person who can also rewrite the rule. For the control the plan calls the strongest in the product, that is three holes in one branch.

So: both finalization points re-run `decide()` with freshly loaded policies, trust, health and bundle, and the new verdict must be no more permissive than the original — otherwise DENY with reason `policy_changed_since_request`, recorded as its own trace check so the operator sees which gate moved. The `ApprovalRequirement` is persisted at decision time as typed columns on `access_requests` (`approval_role`, `approval_count`, `approval_distinct`) and copied to `approvals` from there, demoting the `DecisionTrace` back to the explanation artefact it is documented to be. `requiredCount` becomes enforced n-of-m with distinct attested approvers, and the admin override at `:437` is removed — an admin approves because a rule names their role, not because of who they are. `currentPermissions` at `:526-527` and `timetravel.ts:57` both hardcode `riskTier: "low"`, so the UI's own preview of what you may do is computed as if no risk existed; both take the live tier, and time-travel takes the tier recorded on the request it is replaying.

### 4.8 The latency budget

There is no benchmark in this repository, so the engine has no published number and this plan does not invent one. What can be said from the code is its shape: `decide()` performs one linear scan of `input.policies` with two stable sorts and no allocation beyond the trace, and it is the cheapest thing on the request path by orders of magnitude. The cost is everything around it. Each request re-reads and Zod-re-parses every active policy version — `PolicySpecSchema.parse` at `store.ts:22`, inside `toPolicyVersion`, which `listActivePolicyVersions` (`:29-36`) maps over every row on every call — fires four risk queries (`risk/service.ts:31-49`), and then unconditionally calls `recomputeAssetTrust` (`access/service.ts:168`), which is eight queries plus a conditional ninth plus a storage integrity read (`trust/service.ts:57-99`), even for a denied metadata view that changed nothing.

Three decisions, in order. **One:** the compiled PolicyBundle is cached in memory keyed by a per-tenant `policy_epoch` and invalidated on write, turning N Zod parses per request into a pointer read; the invalidation transport is S6's problem, and the engine-side contract is only that a cached bundle is immutable and carries its own hash, so a stale cache is detectable rather than merely fast. **Two:** `recomputeAssetTrust` moves off the request path onto the anchor worker; asset trust is a projection consumed by dashboards, not a precondition of any gate — nothing in `decide()` reads it. **Three:** the decision path is instrumented with a span per stage — device, health, risk, policy-load, decide, persist, proof — so the number is attributable rather than mysterious, and `packages/policy` gains a committed microbenchmark at fixed policy counts so the engine's own cost is a regression test rather than a claim. Measurement, load testing and the published SLO belong to §6; these are the engine-side changes that make one defensible.

### 4.9 Explainability that survives an auditor

The `DecisionTrace` is the best thing in this codebase. Each `TraceCheck` carries `{id, labelKey, params, result, detailKey, signals}` (`packages/contracts/src/index.ts:86-93`) — i18n *keys* plus structured params, never rendered English — which is why one signed trace renders in three locales from `apps/web/src/i18n/`. That contract is preserved verbatim.

Two gaps make it an explanation rather than evidence. First, `DecisionTraceSchema` (`:104-110`) carries `verdict`, `actionClass`, `policyVersion`, `checks` and `reasons` and nothing else — no decision id, no timestamp, no engine version, no input snapshot — so verifying a Proof-of-Action means trusting the surrounding `access_requests` row rather than the signed object. It gains `decisionId`, `decidedAt`, `engineVersion`, `bundleHash` and a canonical hash of the `DecisionInput`, making the decision re-runnable offline from the Evidence Pack alone by a verifier holding the matching engine version — which is exactly why §4.4's semantic changes are `engineVersion` increments and not silent edits.

Second, `reasons` is `z.array(z.string())` and the two most informative entries are built by concatenation — `` `dependency_down:${dep}` `` at `:167` and `` `policy_deny:${top.key}` `` at `:202` — while `checks` carries the identical facts as typed params one field away. The console already pays for this: three separate renderers strip the suffix with `r.split(":")[0]` (`app/access/page.tsx:290`, `app/assets/[uid]/page.tsx:393`, `lib/events.ts:101`) and throw the parameter away, so the operator is told "Dependency unavailable" and "An explicit policy denies it" without ever learning which dependency or which policy, and any Evidence Pack consumer must reimplement the same undocumented colon convention. The i18n file's own header rule reads *"Messages use {placeholders}; never concatenate strings."* Reasons become `{code, params}` objects, matching the shape `checks` already uses, and the three split call sites are deleted. And `no_policy` is suppressed when a deny already explains the outcome: today a single matching deny policy emits both, because the RBAC gate at `:193` fires on an empty `nonDeny` list before the deny gate at `:199-203` fires as well.

### 4.10 The two actions that never touch the engine

`actionClassFor` classifies `policy.edit` and `identity.revoke` as `critical` (`packages/policy/src/index.ts:62-65`), which in `decide()` mandates a 75/60 identity trust floor, an unconditional step-up, and a second distinct attested approver from the critical-class default branch at `:327-328`. None of it runs. Changing the ruleset that governs an entire facility is `requireRole(session, "admin")` at `apps/gateway/src/routes/index.ts:277` — a string comparison, no trace, no Proof-of-Action, no second human. That branch is dead code for precisely the two most dangerous actions in the system, and there are twelve `requireRole` call sites in that one file, each an authorization decision the engine never sees and the Evidence Room never records.

Both actions route through `decide()` with a null-asset `DecisionInput`, and `requireRole` is replaced across the route table by a single `enforce(principal, action, resource)` PEP helper so there is one authorization path in the codebase instead of two that disagree. Two things must land in the same change or it bricks administration on the first deploy. There are no rules for `policy.edit` or `identity.revoke` in any ruleset today, and `decide()` denies with `no_policy` at `:193` when no non-deny rule matches — so `vajra-default-v1` (§4.6) must ship both rules before any route is switched over, and the switch is gated on a test that asserts an admin can still edit a policy. And the default approver at `:328` resolves to `admin` when the requester is an admin, which combined with `ROLE_ACTIONS` granting these two actions to admins alone means a policy edit needs a *second admin* — correct as a control, and a real operational constraint on a facility that has provisioned exactly one. The default rules therefore name `security-admin` as the approver role for `policy.edit` under the six-role set S3 introduces, and tenant provisioning refuses to complete with fewer than two principals able to satisfy it.

### 4.11 Why not Cedar, and what we ship instead

Our rule grammar is narrow and stays narrow: `PolicySpecSchema` (`packages/contracts/src/index.ts:115-149`) allows exactly one `action` per rule (not an array), two resource attributes (`class`, `sensitivity`), three conditions (`hours`, `deviceTrusted`, `maxRiskTier`), and a four-value role enum; `RequestContext.reason` (`:180`) is collected, stored in `access_requests.context` and never read by the engine. It does have to grow, and the growth is already scoped by decisions taken elsewhere in this plan rather than by a wishlist: `subject.role` takes the six per-tenant roles S3 defines, `condition` gains `assuranceLevel` so the WebAuthn attestation class is a first-class policy input rather than an implicit one, and rules gain a project scope per §4.5. Those three land inside `PolicySpec` v2 and are versioned by `bundleHash` like everything else.

What stays out is the class of rule the grammar cannot express at all — "artists assigned to this shot until it delivers", "the owner's manager may approve", "no egress without a ticket reference" — which is relationship and workflow evaluation, not a wider condition set. Cedar is formally verified, has a validator and an analyzer, and is the right three-year answer to that. It is the wrong fourteen-week answer: it consumes the budget, adds a WASM dependency, and buys nothing a pilot buyer asked for. **Decision: Cedar is a written decision record and a `PolicySpec → Cedar` compiler sketch, nothing more. The trigger that changes it is a second design partner blocking on a rule the grammar cannot express** — at which point the PolicyBundle boundary means the compiler slots behind `PolicySpec` without another migration.

The differentiator was never the syntax, and it is not that the alternatives are crude — OPA evaluates arbitrary documents, Cedar returns the determining policies with its verdict, Zanzibar answers relationship questions at a scale we will never need. It is that none of them carries the overlay, because none of them is trying to: trust that decays on evidence (`liveness_failed` −15, `new_device` −8, `incident_opened` −30, clean-day recovery capped at 85, `packages/trust/src/index.ts:59-95`), soft/hard gate pairs per action class that produce STEP_UP rather than a binary, a risk score a dependency timeout can only raise, and an incident overlay that freezes sensitive actions at S2. That produces a third verdict — STEP_UP — which is what makes a receipt worth signing, because the receipt records that a specific human passed a server-checked presence test seconds before the bytes moved.

So the engine ships two ways. `POST /v1/decide` behind an OpenAPI 3.1 spec generated from the `@vajra/contracts` Zod schemas, with generated TypeScript and Python clients, for PEPs that can make a call. And `@vajra/policy` built with `tsup` into dual ESM/CJS plus `.d.ts` — replacing today's `"main": "./src/index.ts"`, `"exports": {".": "./src/index.ts"}` and `"build": "tsc --noEmit -p tsconfig.json"`, with a conditional exports map (`development` → `./src/index.ts`) so `pnpm dev` keeps its source-linked DX — for a Node PEP that fetches the signed bundle and evaluates in-process, OPA-sidecar style. Both cite the same `bundleHash` and the same `engineVersion`. Both are re-runnable from the trace.

## 5. Evidence, compliance and the auditor product

Everything else in this plan is table stakes a competitor can copy in a quarter. This section is the moat: an artefact whose validity does not depend on VAJRA being alive, honest, or reachable. The current build has the right cryptographic bones and the wrong trust topology — `verifyProof` at `apps/gateway/src/modules/proof/service.ts:125` checks a Proof-of-Action's signature with `ctx.keys.publicKey`, the issuer's own in-process key, so today a studio's auditor gets a boolean from the party under investigation. `ISSUER_DID` defaults to `did:web:vajra.local` (`apps/gateway/src/config.ts:46`), which does not resolve. Worse, one key pair derived at `apps/gateway/src/app.ts:38` from `PROOF_SIGNING_SEED` signs Proofs-of-Action, Evidence Packs, download manifests *and* identity VCs (`identity/vc.ts:22-28`), none of which carry a `kid`. Fixing that topology is the work of this section. Almost none of it is new engineering hours: the erasure and commitment work rides inside the tenancy/chain-v2 XL in §2, the key hierarchy rides inside the custody-broker/key XL, and the only genuinely new, separately schedulable deliverable here is `@vajra/verify` plus the published trust root — small, parallelisable, and the one thing a buyer sees.

### 5.1 Threat model, and the sentence that closes it — with its preconditions

Four adversaries, in the order a facility's TPN assessor walks them. **The malicious or coerced insider** is countered by policy-gated egress, a second distinct approver attested by a hardware authenticator, and a Proof-of-Action naming both humans. **The credential thief** is countered by the session controls in §3 and by possession of a capability no longer being the whole of the authorization. **The compromised administrator** is countered by routing `policy.edit` and `identity.revoke` through the PDP (§4). **The platform operator — us** is the adversary this section exists to neutralise, and the only one a studio actually asks about. The answer is one sentence, stated verbatim in the security pack: *a compromised VAJRA operator can suppress future evidence but cannot forge or silently alter past evidence.*

Say it, then immediately state its three preconditions, because an assessor who finds them himself stops believing the sentence. It holds when (i) the verifier obtained the tenant's JWKS out of band and not from the compromised deployment, (ii) the artefact was anchored before the compromise, and (iii) key custody is BYOK in the customer's own KMS, or the anchoring cadence bounds the window. The residual is explicit: *everything between the last published chain head and the compromise is forgeable, and an hourly cadence means that window is at most one hour.* In the facility single-box topology the tenant holds its own KMS key and the sentence is unconditionally true; in studio-oversight SaaS on our KMS it degrades to "cannot alter past evidence anchored before the compromise", and that degradation is written into the topology comparison, not hidden. "We are trustworthy" is not an answer. A bounded, dated, mechanically checkable sentence is.

### 5.2 The artefact at v2: stop mutating what you signed

`ProofOfActionBodySchema` (`packages/contracts/src/index.ts:223-242`) carries actor, asset, policy ref, trust, risk, hashed device id, liveness attestation hash, approvals, the full `DecisionTrace` and the audit anchor. It carries no version, no tenant, no key identifier and no engine provenance. v2 adds `schemaVersion`, `tenant`, `project`, `kid`, `alg`, `bundleHash`, `engineVersion` and `inputHash`. Two constraints on that list. `tenant` and `project` are opaque ULIDs plus salted commitments, never facility or title names — a studio holding packs from twenty vendors must not be able to correlate them, and cleartext identifiers in a hashed body contradict the Tier B rule in §5.7. And `inputHash` alone does not make a decision "re-runnable offline": that requires the `DecisionInput` and the PolicyBundle too. The Evidence Pack therefore embeds `vajra-default-v1` by value (it is public) and the redacted inputs; the Proof-of-Action on its own supports *re-verification* of `bundleHash` and `traceHash`, not replay. Claim the weaker thing accurately. While the schema is open, `device` — today an unsalted `sha256Hex(deviceId)` at `proof/service.ts:70` — becomes an HMAC commitment under the same subject salt, or the artefact we hand a third party is itself the correlation oracle §5.7 exists to remove. Certificate ids stop being minted by `COUNT(*)` (`proof/service.ts:45-50`), which is racy and publishes our total issuance volume to every recipient.

The second change is structural. `refreshProofsForAuditEvent` (`proof/service.ts:104-114`) rebuilds the body with the freshly-landed `ledgerTxId` and `block`, re-signs it, and issues `UPDATE proof_certificates SET body, body_hash, signature, updated_at` on the existing row. The same `cert_id` ends up with two different bodies and two different *valid* signatures, and the earlier one is destroyed. An opposing expert does not need to break our cryptography; they need only demonstrate that the issuer edits artefacts after issuance, and the corpus loses standing. Replace it: issue with `anchorStatus: "pending"` and the anchor fields null, then when the outbox lands emit a **separately signed anchor attestation** — `{certId, bodyHash, eventId, ledgerTxId, block, anchoredAt, kid}` — that a verifier staples to the original. Binding it to `bodyHash`, not just `certId`, is what stops an attestation being lifted onto a different body. `anchorStatus` becomes a first-class *third* verification state rather than a failure: an unanchored Proof-of-Action is **valid but not yet ordered**, because otherwise every artefact reads red for the seconds-to-hours before the outbox drains. `proof_certificates` (`db/schema.ts:296-306`) then becomes append-only in practice as well as principle — enforced by revoking `UPDATE` and `DELETE` on the evidence tables from the application role, a control an assessor can verify in `information_schema` in ten seconds.

`evidence_packages` (`db/schema.ts:326-334`) has no `updated_at` and is often called immutable. It is not, in the way that matters: `GET /v1/incidents/:id/evidence` (`routes/index.ts:351-354`) *inserts* a signed row on every read (`proof/service.ts:239`) with an id minted from `COUNT(*)` (`:197`), so refreshing the page mints a second Evidence Pack for the same incident with a different `generatedAt`, a different hash and a different signature. Nothing looks worse in discovery than five differently-signed packs for one incident. It becomes `POST`, idempotent on content hash, returning the existing pack when the inputs are unchanged.

### 5.3 Published trust root, and splitting one check into two

Serve `GET /.well-known/jwks.json` and `GET /.well-known/did.json` per tenant, listing every `kid` with its algorithm and validity window. Verification resolves the `kid` carried in the artefact against the published key set **including retired keys**, instead of comparing against whatever the process holds in memory.

While in that file, split one check into two. Line 125 reads `ed25519.verify(ctx.keys.publicKey, bodyHash, signature) && body.issuer === ctx.keys.issuerDid` and reports the conjunction as `verify.signature_bad`. That is a lie in the most common case: a facility renaming its deployment from `did:web:vajra.local` to a real domain, or promoting staging to production, instantly turns every historical artefact into "bad signature" when the signature is fine and only the configured name changed. v2 reports `signature` (pure cryptography against the key resolved from the artefact's own `kid`) and `issuer` (is this issuer recognised, and was it trusted at `decidedAt`) as independent results. The issuer alias history that backs it cannot live in a private table, or the verifier is back to calling our API and §5.4 collapses: it is published as a signed, anchored `issuer-history.json` alongside the JWKS, each alias transition an anchored event. The same `kid` treatment goes on the download manifest (`vault/service.ts:223-240`), on the identity VC — which today is signed with no `kid`, no expiry, an unconditional `livenessVerified: true` the server never actually verified, and a hardcoded `org: "The CodePool"` (`identity/vc.ts:17-18`) — and on `verifyEvidencePackage`, whose signature check at `proof/service.ts:251` is weaker still: it checks the signature and never checks the issuer at all.

### 5.4 `@vajra/verify` — the product, not the endpoint

Ship a zero-external-dependency Node package and a single static HTML page that verify a Proof-of-Action or Evidence Pack **with no call to our API**. Apache 2.0, no license key, no telemetry. Two engineering constraints the pitch usually skips. First, do not *reimplement* `canonicalJson` (`lib/crypto.ts:86-103`: recursive key sort, `undefined` dropped, `Date` to ISO) in a second codebase — that is how the hash rule silently diverges. Extract it into `@vajra/canonical`, consumed unchanged by gateway and verifier, with one shared test-vector file that CI runs against both. The frozen spec must pin the behaviours the one-line description hides: `undefined` is dropped from *objects* only (`:96`) and becomes `null` inside arrays (`:91`); `NaN` and `Infinity` serialise as `null`; `BigInt` throws; `Date` is handled only when reached through `sortValue`; and JSON.stringify's own string escaping, lone surrogates included, is part of the rule. It is load-bearing for every `payloadHash`, `chainHash`, `specHash`, `bodyHash` and `packageHash`, so moving to RFC 8785 JCS is a versioned v2 artefact decision, never an in-place change. Second, Node's `crypto.verify` covers Ed25519, but WebCrypto Ed25519 is not universally available in browsers — the static page ships a vendored, pinned, hash-checked Ed25519 implementation, and we state the browser matrix rather than discovering it in a demo. Distribution is a single-file `verify.mjs` plus a checksummed tarball shipped *inside* the Evidence Pack, because `npx` does not work on the air-gapped laptop that is the whole scenario.

`POST /v1/verify/proof` and `/v1/verify/evidence` (`routes/index.ts:337-338`) survive, split rather than simply authenticated — a studio auditor is not a tenant member, so requiring a session would defeat the endpoint's only purpose. The unauthenticated path is bounded and pure: size-capped body, signature and hash checks against the published JWKS, zero database and zero ledger access. The DB-touching checks — chain, ledger anchor, policy hash — require a session, because today `verifyEvidencePackage` loops a ledger round-trip per event (`proof/service.ts:266-279`) and a full `verifyProof`, itself worth up to two more ledger calls, per embedded proof (`:283-287`), over attacker-supplied input on an unauthenticated route. While in that file, `listProofs` (`:96-100`) silently ignores its `requestId` filter via a `filter.requestId ? true : true` no-op, and `buildEvidencePackage` reads the entire `policy_versions` table into memory to filter it in JS (`:189`).

### 5.5 Keys: a hierarchy that can rotate

`kekFromSecret` is `sha256("vajra-kek:" + secret)` (`lib/crypto.ts:194`) and `keyPairFromSecret` is `privateKeyFromSeed(sha256("vajra-ed25519:" + secret))` (`:122-126`) — one unsalted round over a low-entropy passphrase, with `MASTER_KEK` and `PROOF_SIGNING_SEED` defaulting to literals that boot and encrypt (`config.ts:44-45`). Introduce a `KeyProvider` seam mirroring the `StorageDriver` interface at `vault/storage.ts:11-19`: `wrapDek / unwrapDek / sign / getPublicKeys`, with drivers `local` (HKDF-SHA256 over a mandatory ≥32-byte key, refusing the shipped defaults outside the laptop profile), `awskms` and `azurekv`. Hierarchy: provider master → per-tenant KEK → per-version DEK, with `kek_id` and `wrap_alg` per row and the AAD widened from `${assetUid}|${version}` (`vault/service.ts:89`, and again on read at `:216`) to bind the tenant — the columns themselves are §2's, whose only key-related fields today are `dek_wrapped` and `iv` (`db/schema.ts:163-164`). The migration hazard is that changing the derivation orphans every DEK already wrapped: `wrap_alg: "sha256-v1"` therefore stays *readable* forever and is refused for new writes, which is exactly why the recipe is recorded per row rather than in config.

Both rotations then become routine. **KEK rotation** is a streaming re-wrap over small DEKs that never touches a ciphertext blob, running with two active KEKs, progress on a `vajra_rows_on_retired_kek` gauge — online on Postgres, and honestly a stop-the-world job on PGlite's single embedded connection. **Signing-key rotation** mints a new `kid` and marks the old `retired` — valid for verification, refused for new signatures — so every previously issued artefact keeps verifying, and each `kid`'s public key is anchored at activation so key provenance is itself provable. Proof-signing keys and the session JWKS of §3 are separate hierarchies with separate `kid` namespaces; a verifier that accepts a session key for an evidence signature is a finding. BYOK in the customer's own account is the closing answer to "who holds the key", and revoking their CMK is a kill switch they control. FIPS posture is stated per driver and scoped to key operations: `awskms` and Azure Managed HSM are validated modules and are the paths offered to regulated buyers; `local` is Node's built-in crypto and says so on the Assurance Board. We never say "FIPS-validated product" — audit hashing, TLS and the session path run on unvalidated Node crypto regardless of driver.

### 5.6 Anchoring to a log we do not control

Per-tenant chain heads are published hourly into **Sigstore Rekor**, with the inclusion proof stored alongside. Two precisions. Rekor entries are public, so the head itself leaks nothing (it is a hash) but the *cadence and volume* would leak a named facility's activity — heads are therefore published under a single VAJRA log identity with the tenant as a salted commitment, resolvable only by someone already holding the Evidence Pack. And the RFC 3161 TSA fallback (FreeTSA, DigiCert) is not equivalent and is not described as such: a timestamp proves "this hash existed before T", it does not prove membership in an append-only log, so a TSA-only tenant gets the *anti-backdating* half of the property and not the *anti-reordering* half. That distinction is in the security pack, because an assessor will ask. The publisher is a job on the existing single-writer anchor tier (§6), not a new singleton to operate.

### 5.7 Erasure against immutability, resolved concretely

Today `asset.delete` is `tx.update(assets).set({ deletedAt: now })` plus an audit event with an empty payload (`access/service.ts:257-260`). The blob survives, the wrapped DEK survives, and the plaintext SHA-256 was written both into the audit payload (`vault/service.ts:144`) and onto the append-only ledger as the third `AssetPassport.Mint` argument (`:133`). The filename is worse in one place and better in the other: cleartext in the audit payload as `name`, but reaching the ledger only inside `hashJson(passportMeta)` (`:95`, `:133`). A SHA-256 of a document on an immutable log is a permanent confirm-by-hash oracle over the file you claim to have erased, and `StorageDriver` has no `delete()` method at all (`vault/storage.ts:11-19`).

Three tiers resolve it. **Tier C** — chain hashes, payload hashes, sequence numbers — never deleted, never rewritten. **Tier B** — filenames, plaintext SHA-256, device ids, actor and counterparty identifiers — never enter a hashed payload or a ledger argument as cleartext; the payload carries `HMAC-SHA256(subject_salt, value)`, with cleartext in a redactable side table. Salt scope is the detail that decides whether this works: one salt per (tenant, asset) for asset-derived identifiers and one per (tenant, subject) for people, so erasing an asset does not collaterally blind every unrelated event about its owner. **Tier A** — ciphertext blobs and wrapped DEKs. `POST /v1/assets/:uid/erase` — itself routed through `enforce()` with step-up and a second approver, because it is the most destructive call in the product — destroys the asset salt, overwrites `dek_wrapped` with a tombstone, and calls a new `StorageDriver.delete(cid)`. The audit chain still verifies byte-for-byte because it only ever hashed commitments, as does every Proof-of-Action issued before the erasure. That is true of v2 rows only: v1 rows keep cleartext inside the hashed payload and are unerasable by construction, which is precisely why this lands in the same breaking change as chain v2 (§2), before any pilot data exists, and why existing local and demo data is discarded rather than migrated.

The **Certificate of Erasure** must be scoped to what was actually destroyed or it is a liability, not a deliverable. Erasure is a job, not a call: it names the primary database, the object store, and each backup generation still holding a copy, and states the retention date after which the claim becomes unconditional. Where the bucket is the customer's own — which it is, by the custody-plane thesis — object-lock and versioning settings are theirs, and the certificate says so. **Legal hold beats erasure, visibly.** A `legal_holds` row hard-blocks the shred job; the API returns a documented `409 erasure_blocked_by_legal_hold` naming the hold and the matter, and that refusal is itself an anchored signed event. That is the defensible answer to a DPDP s.12 or GDPR Art. 17 request, not an evasion of it. Retention classes with an immutable floor on audit and proof rows, an audited purge job, and `tenants.region` pinning database, bucket and KMS key complete the set. `GET /v1/tenants/:id/compliance` returns retention class, active holds, region, key provider and rotation state: one page to point a reviewer at.

### 5.8 The Evidence Room and what a customer hands their auditor

`verifyAuditChain` (`audit/service.ts:102-117`) already accepts a range and reports the first broken `seq` (`:112`); it is only ever called unbounded, from an unauthenticated `/v1/stats` (`routes/index.ts:63-75`) that rehashes the entire table on every request. Add signed, anchored chain checkpoints every N events so verification replays from the last checkpoint; authenticate `/v1/stats`; and change its chain field from a live boolean to "verified to seq N at time T", which is both cheaper and more honest. `buildEvidencePackage` (`proof/service.ts:180-241`) already assembles the right things — the incident, its ordered events, every cited Proof-of-Action, the exact policy versions in force, and the actor's trust deltas from `openedAt − 1h` to `closedAt` — and `verifyEvidencePackage` re-verifies each embedded proof rather than trusting it. Extend it to per-title assembly (the Chain-of-Custody Evidence Pack), version the body, stamp the `kid`, embed the PolicyBundle and the verifier, and include a **manifest of what the pack does and does not attest to**: no phone-camera defence, no watermark, nothing about assets that never passed the gate. Add streamed NDJSON/CSV export of the active *filter* with a signed manifest and a chain-range proof, replacing the two single-record `data:` URI downloads that are the only exports in the product today (`app/incidents/[id]/page.tsx:352`, `app/verify/page.tsx:237`).

### 5.9 Compliance sequence, and the honesty mechanism

In procurement order: (1) an **MPA/TPN control-mapping report** naming the specific recurring findings VAJRA closes — unique user identification, documented approval on egress, asset tracking, content transfer logging — written as a pilot deliverable; (2) **SOC 2 Type I**, with the distinction stated rather than blurred: Vanta or Drata gives us *readiness evidence* in the pilot window, a Type I *report* needs a CPA firm and four to eight weeks of its own, and the Type II observation window starts in week 1 and is never implied at pilot signature; (3) an **independent web-app pen test**, scoped up front, with report *and* retest letter in the data room — a remediation letter with no retest behind it is theatre; (4) **DPA plus India DPDP and GDPR alignment**. Here the standard pitch overreaches and must be corrected: VAJRA processes plenty of personal data — DIDs, names, device commitments, facility membership, access history — and is a data processor for all of it. The narrow, genuinely strong claim is that *no biometric byte reaches the server*, and the enforcement is not `biometricsStored: 0`, which is a hardcoded literal at `routes/index.ts:89`, echoed as a literal in the onboarding payload at `identity/onboarding.ts:91`, and asserted as a literal by `gateway.test.ts:76` — a self-certifying constant proves nothing. The real enforcement is `LivenessEvidenceShape` at `packages/contracts/src/index.ts:287-290`, which admits only a bounded score and a record of bounded floats, and zod strips everything else before it reaches a payload. That is the invariant to name in the DPA, and it needs hardening in the same commit: the signal keys become a closed enum with a cardinality cap, so `livenessSignals` cannot become a covert channel for a low-resolution descriptor. (5) A completed CAIQ / SIG-Lite maintained as a living document. ISO 27001 is explicitly out of horizon and we say so.

What the customer hands their auditor is not a PDF: it is the Chain-of-Custody Evidence Pack, the `@vajra/verify` binary shipped inside it, and the JWKS. What they hand their *security reviewer* is four runnable things — the 22-table isolation matrix output, a live key rotation with pre-rotation artefacts still verifying, an offline verification with the gateway powered off, and a byte flipped inside an `audit_events` payload causing the verifier to name the exact broken sequence number. Finally, `GET /v1/capabilities` and the persistent **Assurance chip** name every load-bearing claim as real, dev-grade or stubbed — including, until WebAuthn UV lands, that liveness is client-asserted, and that the identity VC currently asserts `livenessVerified: true` on the server's word alone. A reviewer who learns our limits from us buys the rest; one who finds them in a pen test stops believing any of it.

## 6. Platform engineering, deployment and operations

### 6.1 Three planes, one image

VAJRA today is one process. `apps/gateway/src/app.ts` builds everything in a single `buildApp()` — config, DB handle, storage driver, signing keypair, `HealthService`, ledger driver, `OutboxWorker`, routes — and `apps/gateway/src/server.ts` calls it once, seeds if empty, starts the outbox timer, and listens. That composition root is good and stays. What changes is that the same image is deployed under three **roles**, selected by an env var, not by three codebases:

| Role | Replicas | Owns | Tolerates being down |
|---|---|---|---|
| `api` | 3–20, HPA | HTTP, decisions, custody checkout | No — this is the 99.9 % path |
| `anchor` | 1 (`strategy: Recreate`) | The outbox drain, Rekor/TSA publication, deferred trust recomputation | Yes, for hours — publication is at-least-once and converges |
| `control` | 0, invoked as a Job | Migrations, tenant provisioning, KEK re-wrap | Not applicable — it is not a server |

`server.ts` gains a `ROLE` switch: `api` never calls `ctx.outbox.start()`; `anchor` starts the drain and does not `app.listen()` on the public port; `control` runs one command and exits. Two details are load-bearing and easy to get wrong. First, `OutboxWorker.start()` calls `this.timer.unref()` (`modules/ledger/outbox.ts:50`) — an `anchor` process that does not listen has *nothing* holding the event loop open and would exit within milliseconds of boot, so the anchor role must ref its timer (it also needs a bound admin listener for `/healthz`, which supplies the handle anyway). Second, a `replicas: 1` Kubernetes Deployment under the default RollingUpdate briefly runs *two* pods; `anchor` must be `Recreate` (or a StatefulSet with `OrderedReady`), which is the mechanism behind the stop-then-start of §6.7.

Be precise about what the role split buys, because an architecture reviewer will press on it. The leasing change in §6.2 is what makes N anchor replicas *correct*; `replicas: 1` is a deliberate choice about ordering determinism, Rekor call volume and cost, and it is the ceiling we publish rather than hide: *horizontally scaled API tier, one anchoring writer, per-tenant chains, measured throughput stated out loud.* Claiming the deployment invariant is what fixes the outbox would be claiming a config file fixes a race.

**What actually breaks today at two replicas.** Five things, all verifiable in the repo. (1) `OutboxWorker.tick()` selects `status='pending' AND attempts < 25 ORDER BY created_at LIMIT 20` with no row lock (`outbox.ts:80-85`), so both replicas submit the same rows; the loser gets a deterministic `ChainError`, is written `status: 'failed'` (`:101`), and `patchRef` (`:93`) never runs — so `audit_events.ledger_tx_id` stays null forever for an event that *is* anchored. (2) `DB_MODE` defaults to `pglite` (`config.ts:15`), an embedded single-process database — two replicas have two private databases. (3) `STORAGE_MODE` defaults to `fs` writing to `./storage` (`config.ts:29-30`), so a blob written on replica A 404s on replica B; `createStorage` (`modules/vault/storage.ts:162-173`) offers only `memory`, `ipfs`, `pinata` and `fs`. (4) `HealthService` caches for 3 s and holds `simulated` outages in a per-process `Set` (`modules/health/service.ts:14,20`), so a drill toggled on one replica is invisible to the other. (5) `createDb` calls `await migrate(...)` unconditionally on both the postgres and pglite paths (`db/client.ts:28,56`) and drizzle's migrator takes no advisory lock; today's baseline survives only because `0000_small_blue_shield.sql` is 24 `CREATE TABLE IF NOT EXISTS` and 37 `IF NOT EXISTS` clauses in total.

Fixes, in order. An S3-compatible `StorageDriver` (S3, Wasabi, B2, MinIO — one driver, four endpoints) becomes the production default; `fs` is retained for `laptop` and `memory` for the harness, and IPFS/Pinata are deleted, taking `createStorage` from four drivers to three. This is not a default flip: existing `fs` blobs are content-addressed and their DEK AAD binds the tenant (S5), so the driver lands *with* the custody broker, where the bucket is the customer's to begin with. `DB_MODE=postgres` becomes a boot assertion whenever replicas > 1. Drill state moves to a tenant-scoped row (S2) read behind the existing 3 s snapshot cache — behind it, not beside it, because `depsForDecision()` (`health/service.ts:80-83`) runs on every decision and must not gain a query.

### 6.2 Locks and the outbox at scale

Two global mutexes exist: `pg_advisory_xact_lock(4242)` on every audit append (`modules/audit/service.ts:32`) and `pg_advisory_xact_lock(4343)` on every lite-ledger block (`modules/ledger/lite.ts:56`). Each is held for the *duration of the writing transaction*, so every tenant's writes queue behind every other tenant's and one slow transaction stalls the platform. Both become row locks taken `FOR UPDATE` inside the same transaction. They are not, however, the same row: the audit chain moves to `tenant_chain_heads` (schema in §2), while `ledger_blocks` (`db/schema.ts:359-370`) is a *global* chain — `number` bigint primary key, `prev_hash`, no tenant column — so the lite driver takes its own heads row, per tenant where a tenant chain exists. Conflating the two locks is how this change ships broken. The operational argument, beyond correctness: a row lock is transactional, releases with the transaction, is visible to an SRE in `pg_locks` joined to `pg_class` rather than as an opaque integer, and — decisively — it avoids the namespace hazard, because the one-int and two-int forms of `pg_advisory_xact_lock` occupy *different* lock spaces and would not exclude each other during a rolling deploy. Row locking needs no cutover window; the advisory-form migration would need one.

The outbox is a genuinely good pattern (rows enqueued in the caller's transaction, `enqueueLedger` at `outbox.ts:22-28`) with four production defects. It gains `locked_by`, `locked_until`, `next_attempt_at` and a `dead_letter` status on `ledger_outbox` (`schema.ts:338-356`, which today carries only `attempts`, `status`, `last_error`, `tx_id`, `block` as control columns), claimed with `UPDATE ... WHERE id IN (SELECT id ... FOR UPDATE SKIP LOCKED LIMIT 20) RETURNING *`, and its index changes from `(status, created_at)` to `(status, next_attempt_at)`. The fixed 500 ms `OUTBOX_INTERVAL_MS` (`config.ts:49`) with a hard `attempts < 25` ceiling burns one attempt per tick and breaks the round on the first transport error (`outbox.ts:103`), so 25 attempts elapse in roughly 12.5 seconds — a peer or database restart longer than that strands rows permanently and invisibly, because `pendingCount()` counts them as merely pending. Replace with exponential backoff plus jitter on `next_attempt_at`, no attempt ceiling, and `dead_letter` after a configurable wall-clock horizon with an authenticated requeue endpoint.

And `already_anchored` — raised by `AuditTrail.AnchorEvent` and `PolicyRegistry.AnchorPolicyVersion` in `@vajra/chain-logic` (`packages/chain-logic/src/index.ts:277`) — is treated as **success**. One correction to how, because the obvious phrasing is not implementable: the on-chain `AuditRecord` is `{ eventId, chainHash, type, summaryHash, anchoredAt }` (`index.ts:278`) and carries **no tx id**, so re-reading it cannot supply `patchRef`. The tx id is recovered from `ledger_state_history` (`schema.ts:379-390`, keyed `(key, id)` with `tx_id` and `block` per write) for the internal driver, and from a history query for any external one. That lookup is the one primitive that turns the worst bug in the file into self-healing convergence, and it is the foundation of `vajra doctor --reconcile` (§6.7).

Process hygiene ships with it. `tick()` is fired as `setInterval(() => void this.tick(), ...)` with a `try/finally` and no `catch`, and its outermost awaits are DB calls — a two-second Postgres failover escapes as an unhandled rejection. So does `void ctx.outbox.drain()` at `server.ts:18`, fired unawaited before `listen()`. There is no `process.on('unhandledRejection')` anywhere in `apps/gateway/src`; the only `process.on` in the entire codebase is the SIGINT/SIGTERM pair at `server.ts:26-31`. So: a `catch` inside `tick`, process-level `unhandledRejection`/`uncaughtException` handlers that log structured and increment a counter, and a circuit breaker around the ledger driver surfaced on `/readyz`.

### 6.3 The ledger decision

Hyperledger Fabric leaves the plan. `FABRIC_PEER_ENDPOINT` is a single `host:port` string (`config.ts:23`) with no peer list and no discovery; `fabric/` contains exactly two bash wrappers (`network-up.sh`, `network-down.sh`) around `fabric-samples`, with no `configtx.yaml`, no orderer/raft topology and no CA config; and `FabricLedger.health()` (`modules/ledger/fabric.ts:73-80`) only calls the memoised `ensure()`, which returns the cached `Contract` (`:25-27`), so once connected a dead peer reports `ok: true` forever — silently defeating the fail-closed gate, since `HealthService.depsForDecision()` feeds that boolean straight to the PDP. It also needs Docker on a laptop that has none.

Removed means removed, not unregistered. `@hyperledger/fabric-gateway` and `@grpc/grpc-js` sit in `apps/gateway/package.json` **dependencies**, so a driver "left in the tree" stays in the production image and in every Trivy report; both move out with the file, alongside `@fastify/swagger` and `@fastify/swagger-ui`, which are dependencies that `apps/gateway/src` never registers. What replaces Fabric is a per-tenant signed hash chain plus **anchoring**: an hourly `anchor`-role job publishes each tenant's chain head into Sigstore Rekor, storing the inclusion proof, with an RFC 3161 TSA (FreeTSA / DigiCert) as fallback and a no-op sink for `airgap`. The `LedgerDriver` seam and the written-once-executed-twice property of `@vajra/chain-logic` are kept intact. Trigger to reverse: a signed contract clause naming a consortium ledger, at which point Fabric is a Sovereign-tier engagement priced separately, not a pilot deliverable.

### 6.4 Zero-downtime migrations

Migration moves out of `createDb`. A new `apps/gateway/scripts/migrate.ts` (`"db:migrate": "tsx scripts/migrate.ts"`, alongside the existing `db:generate` — there is no migrate script today) takes `pg_advisory_lock(778811)`, runs drizzle's `migrate()` against `migrationsFolder` (`db/client.ts:18`), and releases; it runs as the `control` Job or a compose pre-step. In `db/client.ts` the inline `await migrate(db, ...)` is kept for `pglite` and `memory` (`:56`) — that is precisely what preserves the laptop profile and the in-process e2e harness — and removed for `postgres` (`:28`), replaced by `assertSchemaVersion()`, which reads `drizzle.__drizzle_migrations` and fails fast if the schema is behind, and serves with a warning if it is exactly one migration ahead, refusing two or more. Ahead-tolerance is only safe under expand/contract, so expand/contract is enforced by a CI guard that rejects any generated migration containing `DROP COLUMN`, `DROP TABLE` or a narrowing `ALTER` without an explicit `-- vajra:contract` marker. The journal (`drizzle/meta/_journal.json`) has exactly one entry, `0000_small_blue_shield`, so this pipeline has never been exercised with an incremental migration — the tenancy change is the first, and it is the one that must not CrashLoopBackOff a replica mid-deploy. One consequence lands in CI: the Postgres leg of the isolation matrix (§6.8) can no longer rely on `buildApp` to create its schema and gains an explicit `pnpm db:migrate` step before the harness boots.

### 6.5 Profiles and the three topologies

`VAJRA_PROFILE` (`laptop` | `vpc` | `saas` | `airgap`) joins the five existing driver switches in `apps/gateway/src/config.ts`, with a `profiles.ts` supplying defaults and a boot-time `assertProfileInvariants()` that refuses to start on: any of `SESSION_JWT_SECRET`, `MASTER_KEK`, `PROOF_SIGNING_SEED` still at its shipped dev default outside `laptop`; demo or dev-IdP enabled outside `laptop`; `STORAGE_MODE=fs` or `DB_MODE=pglite` with replicas > 1; `KEY_PROVIDER=local` outside `laptop`/`airgap`. This matters because every secret in `config.ts:42-45` has a working default *and* `DEMO_MODE` defaults to `true` (`:48`), and the demo surface is not merely present under that default — `/v1/demo/outage` (`routes/index.ts:482`) and `/v1/demo/drain` (`:490`) are gated by `requireDemo()` (`:436-438`), which checks `DEMO_MODE` and nothing else, so a forgotten env file ships a deployment where an *anonymous* caller can trip the fail-closed gate. One profile object is the single thing a customer's config audit inspects.

**laptop** — `pnpm install && pnpm dev`, `pglite` + `fs` + internal ledger + local key provider + in-process OIDC, self-seeding, no Docker, no WSL. Shipped tier, not a dev convenience. **vpc (the facility single-box)** — one `docker-compose.yml`: `api`, `anchor`, `web`, Postgres 16, Caddy for TLS, MinIO optional; the facility's own bucket and IdP reached outbound only, no inbound internet exposure. This is the pilot topology and the only one that earns the first cheque. **saas** — Helm on EKS, `api` and `anchor` as Deployments and `control` as a Job, Aurora/RDS Postgres Multi-AZ behind PgBouncer in transaction mode (safe precisely because the tenant GUC is transaction-local), S3 + KMS, Redis for rate-limit buckets. **airgap** is deferred past the horizon and sold as roadmap.

One prerequisite is shared by `vpc` and `saas` and is bigger than it looks. `apps/web` sets no `output` field in `next.config.mjs`, so it is a real Node server under `next start` — good, because that is what can serve a runtime `/config.json`; it gains `output: 'standalone'` for a lean image. But the build-time inlining is not one variable: `api.ts:25` reads `NEXT_PUBLIC_GATEWAY_URL`, and `LivenessCapture.tsx` reads `NEXT_PUBLIC_LIVENESS_MIN_SCORE` (`:45`), `NEXT_PUBLIC_LIVENESS_ENFORCE` (`:47`) and `NEXT_PUBLIC_LIVENESS_MODE` (`:78`, `:177`). All five move behind `/config.json` fetched at boot, or one image still cannot serve two environments.

### 6.6 Observability, SLOs and backpressure

`apps/gateway` has zero observability today — grepping for `opentelemetry`, `prom-client`, `healthz`, `readyz`, `helmet`, `rate-limit`, `under-pressure`, `trustProxy`, `unhandledRejection` and `uncaughtException` across `apps/gateway/src` and its `package.json` returns nothing, and `app.ts` registers exactly two plugins (`@fastify/cors`, `@fastify/multipart`, `:75-81`) and sets no hooks. Added: `@opentelemetry/sdk-node` with fastify/pg/undici auto-instrumentation and explicit spans per decision stage (device, health, risk, policy-load, decide, persist, proof), exporting OTLP with a no-op exporter for air-gap; `prom-client` on a separate admin port 9464; an `onRequest` hook that adopts or mints `traceparent`/`x-request-id`, binds it to `req.log`, and echoes it in the existing single error envelope (`app.ts:83-91`, which already maps `ApiError`/`ZodError`/`ChainError` to stable codes and is a real asset); and pino `redact` for `authorization`, cookies, `contentToken` and attestation payloads.

Client IP needs both halves of its fix stated, because one alone is a false fix. `trustProxy` is a Fastify *factory* option, set at `app.ts:28-34` and nowhere else, and it must be the ingress CIDR rather than `true` — but setting it does not change `routes/index.ts:41`, which reads `req.headers["x-forwarded-for"]` directly and would keep feeding an attacker-controlled string into the risk score. The header read is deleted and replaced with `req.ip`.

RED metrics per route, plus six domain gauges that map to contractual promises rather than to Node internals: `vajra_outbox_pending`, `vajra_outbox_dead_letter`, `vajra_oldest_pending_drain_seconds`, `vajra_decision_duration_seconds{stage}`, `vajra_chain_verified_seq`, `vajra_rows_on_retired_kek`. A Grafana dashboard JSON and Prometheus alert rules ship in `infra/observability/` as deliverables — a customer's SRE handed a dashboard on day one becomes a champion.

The published SLOs separate two things the first draft of this plan ran together, and the locked vocabulary forces the distinction: **drain lag** is the internal chain catching up, **anchoring** is Rekor. Since publication is hourly (§6.3), a "p95 event-to-anchor under 10 s" would be arithmetically impossible. So: `decide()` p99 under 1 ms; `POST /v1/decide` p99 under 25 ms; `POST /v1/authorize` p99 under 250 ms; custody checkout p99 under 400 ms; **drain lag** p95 under 10 s with an alert at oldest-pending over 120 s; **anchor freshness** p95 under 90 minutes with an alert at 3 hours; availability 99.9 % on the decision path (43 minutes/month) and 99.5 % on the anchor path — which is the honest reading of "anchor tolerates being down": decisions never block and the chain keeps growing, only publication lags, and the lag is bounded by the freshness SLO rather than by hope. Error-budget policy: burning more than half in a month freezes feature work for hardening.

These numbers are reachable because §4 removes the per-request ruleset re-parse and moves `recomputeAssetTrust` to the `anchor` role; S6 measures and defends them. Defends, specifically, as a **regression gate**: k6 in CI runs against a committed baseline JSON and fails on a percentage regression, because a shared GitHub runner driving PGlite cannot certify a production p99 and any plan that claims otherwise is inviting the reviewer to say so. The absolute figures are re-measured on the pilot's own hardware in week 1 and written into the pilot report; no latency figure appears in this plan that is not either measured in the repo or explicitly labelled a target.

Backpressure is currently absent, and three unauthenticated endpoints are the reason it is urgent. `/v1/health` (`routes/index.ts:58-61`) calls `snapshot(true)`, deliberately bypassing its own 3 s cache to force all four probes, then adds `pendingCount()` — and `AppShell.tsx:80-96` polls it every 20 seconds from every open tab, so the console is its own load generator. `/v1/stats` (`:63-90`) runs ten count queries, a percentile scan and `verifyAuditChain(ctx.db)` with the `fromSeq`/`toSeq` parameters it already has (`modules/audit/service.ts:102`) left at their defaults, loading and rehashing every audit event ever written. And `/v1/demo/outage` flips the fail-closed gate with no session at all. Added: `@fastify/helmet`; token buckets in two explicitly ordered layers, because the tenant is not known until S3's session `preHandler` runs — per-IP at `onRequest`, per-tenant and per-principal at `preHandler` from tenant entitlements (Redis in `saas`, in-memory on `laptop`); `under-pressure` returning 503 with `Retry-After` on event-loop delay; a configurable pool with `statement_timeout`, `idle_in_transaction_session_timeout` and `application_name` replacing the hardcoded `new pg.Pool({ connectionString, max: 10 })` at `db/client.ts:26`; a cheap `/healthz` and a cached `/readyz` split out of `/v1/health` (which stays, cached and authenticated, as the Assurance Board feed); and `/v1/stats` authenticated and backed by the signed checkpoint delta from §5.

### 6.7 Backup, DR and shutdown

Three stores diverge independently: Postgres (chain, outbox, wrapped DEKs), the object store (ciphertext), and the anchor log. Restoring Postgres to a point before a publication committed leaves the database saying un-anchored while Rekor says anchored — permanently, under today's code. So: `vajra backup` takes a coordinated snapshot recording `pg_dump`/PITR base plus, per tenant, `(audit seq, chain head hash)`, the ledger block height, and a blob CID manifest, under one signed manifest; `vajra restore --verify` replays chain verification and *prints the divergence window* rather than pretending there is none; `vajra doctor --reconcile` walks `audit_events WHERE ledger_tx_id IS NULL`, resolves each against the anchor log and `ledger_state_history`, and repairs the database from it — deterministic because the anchor is authoritative and because `already_anchored` is now a success path with a tx id it can actually find. Published: `vpc` RPO 15 min / RTO 4 h on nightly `pg_dump` plus WAL archiving; `saas` RPO 5 min / RTO 1 h on RDS PITR. Key loss is documented as data loss with a hard boundary — Shamir 3-of-5 escrow for the `local` provider, multi-region CMKs for KMS — and the DR drill is rehearsed quarterly with the restore evidence stored as a signed artefact.

Shutdown today is `outbox.stop()`, which only clears the interval (`outbox.ts:53-56`), then `app.close()`, `ledger.close()` and `dbHandle.close()` (`app.ts:100-105`), fired from a handler that calls `process.exit(0)` with no drain delay (`server.ts:26-31`) — so a tick already executing has the database pulled out from under it on every deploy. Replaced by: flip readiness red → sleep `preStopDelay` → await outbox quiesce and lease release, bounded → `app.close()` with a hard timeout → close drivers → exit. Blue-green at the ingress for `api`; `Recreate` for `anchor`, because a few seconds of drain lag sits well inside the freshness SLO.

### 6.8 Release engineering, and keeping the laptop honest

There is no deployable artefact. `apps/gateway/package.json` sets `"build": "tsc --noEmit -p tsconfig.json"` and `"start": "tsx src/server.ts"` with `tsx` in `devDependencies`; `tsconfig.base.json` sets `"noEmit": true` globally; all four workspace packages point `main`/`types`/`exports` at `./src/index.ts` and define `build` as `tsc --noEmit`. `pnpm install --prod && pnpm start` therefore cannot run. `infra/` and `db/` are empty directories and there is no `.github`. Fixed by: tsup bundling the gateway to `dist/`, externalising `pg` and marking `@electric-sql/pglite` external-and-optional so the WASM payload rides only in the laptop image — the dynamic import at `db/client.ts:44` already permits it, but tsup must be told or it will pull it in; the four packages emitting dual ESM/CJS + `.d.ts` behind a conditional exports map (`development` → `./src/index.ts`, `default` → `./dist/index.js`) so `pnpm dev` DX is untouched; and a multi-stage Dockerfile onto `gcr.io/distroless/nodejs22-debian12`, with the root `engines` field raised from `>=20` to `>=22` so CI and image agree, published per tag with a cosign signature and a syft SBOM.

CI (`.github/workflows/ci.yml`) on every push: typecheck → the **58** unit tests (7 chain-logic, 15 trust, 13 policy, 13 gateway, 10 web — five files, five workspace packages, verified by running `pnpm -r test`; the "35" carried by earlier drafts of this plan is wrong and would have been an embarrassing thing to publish) → the 56-assertion e2e (`apps/gateway/scripts/e2e.ts`, which builds the real app in-process against `DB_MODE=memory`, `STORAGE_MODE=memory`, `LEDGER_MODE=lite` and drives it through `app.inject` — a ready-made gate needing no infrastructure) → `pnpm db:migrate` against a Postgres service container → the 22-table tenant isolation matrix run twice, once on PGlite and once on that container. The two legs prove different things and the difference must be written down: PGlite is a single embedded connection, so it can prove that the RLS predicates hold and that `FORCE ROW LEVEL SECURITY` and `FOR UPDATE SKIP LOCKED` parse and behave for one session, and it can prove *nothing* about contention; only the Postgres leg, with two connections racing the outbox lease, proves the concurrency claim. Then tsup build → Trivy scan → k6 regression gate → axe → signed image publish.

Everything above is constrained by one rule: `pnpm install && pnpm dev` must still bring up a working VAJRA on a Windows laptop with no Docker and no WSL, and `buildApp(overrides)` returning `{ app, ctx, close }` must remain constructible entirely in memory. The published number is boot, not install — cold boot to first served request in under 30 seconds including the 24-table auto-migration and first-run seeding — and it is asserted by a timed CI step, not a README sentence, because install time depends on a PGlite WASM download and the optional `pnpm models:fetch` weights. That constraint is why tenancy uses transaction-local `set_config` rather than a second database role or PgBouncer, why auto-migrate survives for pglite, why the local key provider exists, and why the dev IdP is in-process rather than a Keycloak container. A prospect who evaluates the product in three minutes on their own machine, without a procurement conversation, is the cheapest lead this product will ever get.

## 7. The product surface, integrations and the adoption journey

### The Next constraint is the opposite of what we assumed

Start here, because one line of config invalidates a planning assumption that appears in every prior document about this repo. `apps/web/next.config.mjs` sets `reactStrictMode`, `transpilePackages: ["@vajra/contracts"]`, `eslint.ignoreDuringBuilds: true` and `typescript.ignoreBuildErrors: **false**` — so type errors already fail `next build` and only ESLint is skipped. It does **not** set `output: "export"`, and `apps/web/package.json` starts the app with `next start -p 3000`. This is a Next 15 **server** build, not a static export. Twenty of the twenty-one `page.tsx` files under `apps/web/src/app` open with `"use client"` and fetch in the browser; the twenty-first, `apps/web/src/app/page.tsx`, is a server component that calls `redirect()` from `next/navigation` — the one existing proof that the server layer is present, running and otherwise unused.

That is good news and it forces three decisions. First, there is no static-export prohibition on server code, so the BFF is a change of approach rather than a change of framework: add `apps/web/middleware.ts` (absent today — `find apps/web -name middleware.ts` returns nothing) to guard `/[locale]/{admin,ops,audit,my}/*` on session presence and redirect to sign-in with a `next=` parameter, then move the session into an httpOnly + Secure + SameSite=Strict cookie held by Next route handlers that proxy the gateway. The browser stops seeing a bearer token; `writeCookie` at `apps/web/src/lib/api.ts:49-52` — `path=/`, `samesite=lax`, no `HttpOnly`, no `Secure`, and `setSession` (`:59`) pinning `max-age=3600` against a 15-minute token — is deleted. **The BFF cannot land before S3's OIDC work and must not be scheduled as an independent early win**: an httpOnly cookie is only issuable by a server that terminates the login redirect, and today login terminates in the browser with a DID key held in IndexedDB. The two ship in one commit or the cookie is a cookie holding a token the browser still had to fetch itself.

Second, `apps/web/src/lib/api.ts:25` reads `process.env.NEXT_PUBLIC_GATEWAY_URL`, which the compiler inlines into the client bundle, so one image cannot serve two facilities or two environments. The BFF makes the browser's API same-origin and deletes that variable — but it does not delete the problem, it moves it: the Next server still has to learn the gateway origin at boot, which is S6's runtime `/config.json` and `GATEWAY_ORIGIN` env read, not a build-time inline. Same fix, one layer down, and the client keeps `/config.json` only for non-secret runtime values it genuinely needs (profile name, enabled locales, Assurance chip endpoint).

Third, `useAsync` (`apps/web/src/components/trust.tsx:530-548`, 19 lines, no cache, no dedupe, no retry, no global error policy — and the overview mounts seven of them at once) is replaced by TanStack Query v5. Be precise about what that buys: caching, dedupe, and the end of `AppShell.tsx:76-78` refetching `/v1/me` on every single pathname change. It does **not** own the 401 → refresh → replay interceptor — once the token is httpOnly, refresh happens in the BFF proxy handler, server-side, and the query client never sees a 401 it could act on.

### Four surfaces at four densities

Today there is one console for four jobs. `NAV` in `apps/web/src/components/AppShell.tsx:24-49` is a static const of six groups and fourteen items rendered unconditionally, with no role filtering anywhere, while the gateway calls `requireRole` on twelve routes (`routes/index.ts:104` through `:427`), each throwing `ApiError.forbidden` (`modules/identity/session.ts:65`) into the 403 envelope at `app.ts:83-91`. The result is that an artist sees **People**, **Devices** and **Time travel** in the sidebar and gets blank tables, because twelve call sites across seven files swallow authorization failures into empty arrays — `api.identities().catch(() => [])` at `app/[locale]/app/page.tsx:44`, `activity/page.tsx:33`, `audit/page.tsx:39`, `access/page.tsx:48`, `timetravel/page.tsx:55`, `verify/page.tsx:32` and `components/EntityDrawer.tsx:162`. A buyer reads that as a product without roles.

The split is the **Admin console** (`/admin`), the **Operations console** (`/ops`), the **Evidence Room** (`/audit`) and **My VAJRA** (`/my`), gated by a capability set. `/v1/me` (`apps/gateway/src/routes/index.ts:108-118`) returns `user`, `device`, `permissions`, `incident`, `fresh`, where `permissions` is `effectivePermissions` (`packages/policy/src/index.ts:371-391`) evaluated over `ROLE_ACTIONS` — six asset actions, plus `policy.edit` and `identity.revoke` for `admin`. So it is not quite "only the asset matrix"; what it carries no trace of is tenant, project, or any administrative capability at all. It gains a flat `capabilities: string[]` resolved from the caller's `tenant_members` row against the locked roles — `tenant-admin`, `security-admin`, `operator`, `approver`, `auditor`, `member` — yielding `policy.read`, `policy.write`, `identity.write`, `key.rotate`, `evidence.export`, `drill.run` and siblings. A `<Can action="…">` wrapper filters `NAV` and every action button; `request()` in `api.ts` distinguishes 403 from empty and the surfaces render an explanatory panel. **The twelve catch sites are deleted in the same commit that ships `capabilities` and `<Can>`, never before** — delete them first and the artist trades a blank table for an error banner, which is worse. The rule is absolute: a 403 renders as an explanation and never as an empty table.

Two component vocabularies serve four information densities. `apps/web/src/components/console.tsx` (33 exports: `Panel`, `StatBand`, `DataTable`/`DataRow`/`DataCell`, `EventStream`, `Drawer`, `VerdictStamp`, `StepRail`, `FactorBreakdown`, `AccessMatrix`, `LineageRail`, `TrustHistoryChart`, `DistributionBar`, `OpsHeader`, …) is the dense operator and auditor voice and stays. `ui.tsx` is the editorial voice and becomes the admin and My VAJRA voice — which is also the fix for `/app/settings`, currently the only `/app` screen built from `PageHeader`/`Card` and the one that reads as unfinished.

### API and webhook conventions

Every list endpoint returns `{ items, nextCursor }` with keyset paging (`?after=<opaque>&limit=`, default 50, max 200). This is a breaking change to every caller and to the 56 e2e assertions, so it ships once, inside the same contract break as chain v2 — not drip-fed endpoint by endpoint. The cursor is not invented: the per-tenant chain `seq` is already a total order over `audit_events` and is the natural keyset. Today `/v1/audit` (`routes/index.ts:284-298`) accepts six filters plus `limit` and `order` but no cursor and no offset, so an auditor can filter but physically cannot page past the newest `limit` rows.

`GET /v1/search?q=` handles typed prefixes (`AST-`, `INC-`, `POL-`, `PoA-`, `did:key:`), backing both the console inputs and `CommandPalette.tsx`, which today issues four unbounded full-table fetches on every open (`:50-53`). Search is where the laptop profile bites: PGlite is not a full Postgres extension host, so trigram/tsvector indexes are a Postgres-profile optimisation and the shipped behaviour must be a prefix and `ILIKE` path that is correct — and slower — on `pglite`, verified by the same test on both drivers. The `/v1/identities` N+1 (`routes/index.ts:128-143`: one query for users, then two per user for devices and credential) becomes a single grouped query. Errors keep the existing `{error:{code,message,details}}` envelope from `app.ts:83-91`, plus a correlation id.

Webhooks are signed with HMAC-SHA256 over `timestamp.body` in an `X-Vajra-Signature` header, at-least-once with an idempotency key, exponential backoff, and a per-subscription delivery log — reusing the leased outbox S6 already hardens (`FOR UPDATE SKIP LOCKED`, `next_attempt_at`, dead-letter), not a second delivery engine. Event names are stable: `approval.requested`, `approval.decided`, `egress.completed`, `incident.opened`, `policy.activated`, `identity.revoked`. `chain.verification_failed` and `anchor.dead_lettered` deliberately do **not** ride the tenant webhook bus — a self-reported integrity alarm on a channel the operator controls proves nothing; they surface on the Assurance Board and the SIEM sink, and the anchoring log is what a third party actually checks. OpenAPI 3.1 is generated from `@vajra/contracts` and actually served — `@fastify/swagger` and `@fastify/swagger-ui` are declared at `apps/gateway/package.json:21-22` and imported nowhere in `src` — with a generated TypeScript SDK and the `vajra` CLI (`policy plan|apply|export`, `backup`, `verify`) as the machine surface.

### Integration catalogue

Ship three, certified end to end: **Microsoft Entra ID** (OIDC + SCIM, whose engineering is S3's — this section owns only its admin screens and its place in the catalogue), **an S3-compatible object store** (Wasabi, Backblaze B2, MinIO, S3 — the broker target and the ingest source), and **Slack**. Second rank, ship only if the buffer survives: Microsoft Teams, Splunk HEC and Microsoft Sentinel sinks, Jira Service Management. Deferred with a written reason: Okta (best-effort on the same OIDC/SCIM code path, not certified), Jamf and Intune posture webhooks, Autodesk Flow Production Tracking, Signiant and Aspera transfer-completed webhooks, NexGuard watermark-ID binding, and PagerDuty. Every one of these is an integration a buyer will ask for; only the first three are integrations the pilot fails without.

### Day 0, 1, 30, 90

**Day 0** is a Docker-less laptop: `pnpm install && pnpm dev` (already the root script, running gateway and web in parallel), `packages/dev-idp` signs you in through a real OIDC flow, and a seeded sandbox tenant holds one project and a handful of controlled files. Two things make this faster than today rather than slower: deleting the face path removes the `models:fetch` model download from first run, and `pnpm dev` stops depending on a demo seed nobody can un-seed. First-run time is a CI gate — a timed clone-to-verified-receipt script that fails the build when it regresses — not an aspiration in a slide.

**Day 1** is `/admin/setup` — a server-persisted activation checklist with progress in the sidebar: create the project, connect Entra, map groups to roles, point at the bucket, publish the policy pack, enrol the first approver's FIDO2 key, verify a receipt. It replaces `/[locale]/demo` as the guided experience, and "load sample data" becomes an explicit, one-click-removable project option rather than a seeded database nobody can un-seed.

**Day 30** is the incident: an S2 opens, the SOC is paged through Slack, the operator replays it on `/ops/incidents/[id]`, and closes with an Evidence Pack.

**Day 90** is the audit: select a title and a quarter in the Evidence Room, export one signed bundle, hand it to the studio.

**The aha moment is none of those.** It is a two-minute sequence at the end of the first demo: hand the prospect a USB stick carrying the Proof-of-Action, the published JWKS snapshot, and the single-file `@vajra/verify` bundle — *not* an `npx` invocation, which needs the registry and therefore the network the demo is about switching off. Then close the laptop lid on the gateway and watch them verify on their own machine, offline, against a key we do not control. Everything else in this section exists to get them to that moment and to keep them coming back after it.

## 8. Pricing, packaging, the 14-week plan and the honest cut list

### 8.1 The metering unit, and four things we deliberately never meter

Price on **attested users** and **titles under custody**. An attested user is someone who can request or approve an egress and holds a credential the server can check — typically 15–25% of a facility's headcount, not the 400-seat artist roster. A title under custody is a `projects` row with at least one asset registered and at least one policy in force. Both track the buyer's own exposure: more people who can move a master, and more productions whose leak would be a seven-figure event.

Four exclusions, each for a reason worth stating out loud in the room:

- **Never per-GB or per-transfer.** VAJRA is a custody control plane; the bytes live in the customer's own bucket by construction (S1, S5). A storage line item invites a comparison against Wasabi at roughly $6/TB/month that we lose on principle, and it would contradict the architecture we spent the pilot explaining.
- **Never per decision or per Proof-of-Action.** Metering the evidence artefact creates a direct incentive for the customer to produce less evidence. That is a pricing model at war with the product.
- **Never per audit event.** Same failure mode, applied to the hash chain.
- **Never by deployment topology.** A "Sovereign / air-gapped" tier is a recurring bundle-rot support cost — pinned images accumulate CVEs and generate tickets forever — dressed up as a premium. We decline it until someone funds the refresh cadence separately. This is also why §8.6 can cut the `airgap` bundle without losing revenue: there was never a line item attached to it. Studio Oversight is priced above Facility because it is a different *tenant role* — a receiving, verifying, mandate-publishing tenant — not because it runs somewhere else.

**One consequence nobody costs and everybody forgets.** A price on attested users and titles is unbillable without a usage report. Nothing in the repo counts either, and `tenant_counters` (S2) is a minting mechanism, not a meter. A signed monthly usage export — attested-user headcount and titles under custody, per tenant, as a CSV the buyer can reconcile — is a contractual S4 deliverable, not a nice-to-have. It is one query and one signature; skipping it means invoicing from a spreadsheet in month two.

### 8.2 Packaging

**Custody Pilot — $45,000, 12 weeks, fixed scope.** One facility tenant, one project, up to 150 named users, up to 25 attested approvers, the facility single-box `vpc` topology, install with our engineer on a call. Paid 50% at signature and 50% at week 6, **50% of the fee credits against the first Facility year** — say that in the order form, because otherwise procurement discovers in month four that year one costs $144k and re-opens everything. Conversion is at a **pre-agreed** Facility price so procurement negotiates once rather than twice.

$45k is calibrated to sit above the threshold at which a thing gets treated as a free trial and quietly ignored, and below the threshold that triggers competitive tender — but that second half is a hypothesis, not a fact, and it cannot be true in both currencies at once. ₹40 lakh at a Mumbai facility is a managing-director signature; $45k at a London or Toronto facility is a departmental one. Validating the local tender threshold is question one in the first three discovery calls, and the Indian-market answer may be a lower fixed price with a shorter scope rather than a discount on this one.

The success criterion is written and testable (§8.3). **The remedy for failing it is not a refund** — a non-refundable fee with a written pass/fail and no stated remedy is the clause procurement strikes first. The remedy is that a failed criterion extends the pilot at our cost until it passes or the buyer walks, with the conversion price held open. That is a stronger commercial position than "non-refundable" and a much easier one to defend in the room.

**Facility — $60,000/yr platform fee**, plus $18/attested user/month, plus $500/title/month for projects under active custody. A 400-seat facility with ~70 attested users and 4 concurrent titles lands at $99,120/yr.

**Studio Oversight — $150,000/yr** for the studio-side tenant that receives, verifies and archives Chain-of-Custody Evidence Packs across up to 20 vendor facilities, with SIEM streaming and the ability to publish a PolicyBundle downstream. This is the mandate engine and the strategic revenue — **and it is priced before it is built.** Nothing in the 14 weeks below constructs cross-tenant PolicyBundle distribution or a multi-vendor oversight surface; S4 ships the single-tenant PolicyBundle and `POST /v1/decide`. What a studio can actually do at week 14 is take an Evidence Pack by hand and verify it with `@vajra/verify` — enough to sell the mandate, not enough to invoice $150k. The number goes on the rate card and into the second-year plan; it does not go into a 14-week revenue forecast.

**Professional services, priced to be declined:** $25,000 for a pipeline integration. The intended path is the SDK and the OpenAPI document (S7); the $25k exists for the buyer who will not walk it. Given that §8.6 cuts the second ingest connector, this is also the only answer a SharePoint shop gets before quarter three — so quote it openly and early rather than discovering the gap at renewal.

**Free forever, and it is strategy rather than generosity:** `@vajra/verify` (Apache 2.0, zero dependencies, no license key, no telemetry), the published JWKS and `did.json`, the OpenAPI 3.1 document, the generated SDKs, and third-party verification of any Evidence Pack by anyone. A receipt has evidentiary standing only if checking it costs nothing and requires no relationship with the issuer. Every studio auditor who verifies one is unpaid distribution.

### 8.3 The pilot contract shape

Three named deliverables written into the order form, not a feature list:

1. A signed per-title **Chain-of-Custody Evidence Pack** covering every egress of the pilot production.
2. An **MPA/TPN control-mapping report** naming the specific recurring findings VAJRA closes — shared accounts on shared workstations, undocumented approval on egress, incomplete asset tracking.
3. The **offline verifier**, delivered as a file the studio keeps.

One success criterion, testable, agreed before signature: *the studio's reviewer independently verifies a sample of the facility's Proof-of-Action receipts on an air-gapped laptop, with VAJRA switched off and without contacting the facility's IT.* A free POC has no internal owner and dies at the security review; a paid pilot with a written pass/fail has a sponsor and a date.

Note the dependency this creates on §8.5: deliverables 1 and 3 and the criterion itself all land in **S3**, at week 11. No pilot can be *signed* against this contract before week 12 and none can *start* before the S3 artefacts exist. The founder's discovery runs from week 3; the first signature is week 12 at the earliest; the first pilot runs weeks 15–26 and converts in month seven. Any plan that implies revenue inside the 14 weeks is lying about the calendar.

### 8.4 Land and expand

Land on one facility's release desk against a conditional or failed TPN assessment — fear with a date on it, approved by two or three people, no committee. Expand along three axes: more titles (billing line one), more attested approvers as the control spreads from egress to review-and-approve (line two), and the studio tier. The studio tier is the compounding asset: once a studio publishes a PolicyBundle its vendors must consume, every facility in that ecosystem needs a Facility licence and our CAC on those collapses toward zero.

Target net revenue retention 140% — and the arithmetic constrains where it can come from. Taking $99k to $139k means finding $40k of expansion on an account with a fixed $60k floor. At $18/user/month, that is 185 additional attested users on a 400-seat facility, which would put 64% of headcount above the 15–25% band in §8.1 and is therefore not available. It has to be titles: roughly seven more concurrent productions at $500/month, or five titles plus a modest approver expansion. So NRR is a claim about **title density per facility**, not about seat growth, and the discovery calls should test exactly that — how many productions does this facility have in flight at once — because if the answer is two, 140% is unreachable and the price per title is wrong.

### 8.8 Risks

**The mandate risk** is the big one: if no studio ever mandates VAJRA, the facility buys once for TPN remediation and churns. Mitigation is structural — the pilot success criterion is written so the facility-side value stands alone, and the first three sales calls test exactly that.

**RLS under PGlite is an unproven assumption, not a settled design.** PGlite is real Postgres, so the isolation matrix can run in-process — but it runs on a single connection as a superuser, and superusers bypass row-level security outright; `FORCE ROW LEVEL SECURITY` does not change that, because FORCE binds the table owner, not a bypassing role. The design therefore needs a non-superuser application role and `SET LOCAL ROLE` in the same preHandler that sets the tenant GUC (S3). That is a two-day spike at the open of week 3 with a written fallback: if PGlite will not do it, RLS becomes Postgres-only, the laptop profile falls back to a compile-enforced `TenantDb` seam, and the matrix runs against Postgres in CI. Discovering this in week 5 instead of week 3 is the single most likely way S1 blows its three weeks.

**FIDO2 budget on the facility floor, corrected.** MPA secure-area rules commonly ban personal phones, so keys must be facility-issued — and the number is not 25. The Facility tier bills 70 attested users, and an attested user is anyone who can *request* an egress, not only approve one. At $50–70 per key that is $3,500–5,000 of hardware plus spares and a replacement process, not the ~$1,500 that "20–25 approvers" implies. The pilot's 25 approvers are the wedge; the expansion path in §8.4 requires the buyer to fund the larger number, and we validate that budget before week 6 rather than at the first renewal.

**The single-writer anchoring ceiling** is real and we publish the measured number instead of pretending it away — one anchoring writer at `replicas: 1`, per-tenant chain serialisation replacing today's global `pg_advisory_xact_lock(4242)` in `apps/gateway/src/modules/audit/service.ts:32` and `(4343)` in `apps/gateway/src/modules/ledger/lite.ts:56`.

**The S1 cutover is indivisible** — chain topology, payload commitments and the tenant key prefix in `@vajra/chain-logic` move together, in one window, with a tested restore.

**Compliance calendar, honestly.** SOC 2 Type II needs a 6–12 month observation window, and you cannot observe a control set that is being replaced underneath you: identity, access control and key management all change between weeks 3 and 11. What starts in week 1 is the *evidence habit* — change management, access review, ticketing, the CI gate as a control. The Type II observation window opens when the control set stabilises, which is week 12 at the earliest. At pilot signature we sell Type I readiness plus a pen test plus the isolation matrix output plus the verifier, and claim nothing more.

**Key custody**: BYOK into the customer's own AWS account from S3 onward, with key-loss consequences written into the runbook in plain language.

**Scope**: the realistic failure mode is week 14 with six things 80% done, which is what the cut line exists to prevent — and why week 14 admits no new scope.

**Stale documentation is itself a risk.** `docs/HOW-IT-IS-BUILT.md:494` advertises "35 unit tests" against an actual 58, and the chaincode suite reports success without running anything. A buyer's engineer who greps the docs against the repo finds the discrepancy in five minutes, and every honesty claim in §8.9 gets discounted at once. The docs are regenerated from CI output in S0.

### 8.9 The nine-minute demo

Eight prove points, run in order, without a reset — and the running order is load-bearing, because points 5 through 7 mutate state that points 1 through 4 depend on.

**(1)** The 22-table isolation matrix runs live against the `memory` driver in-process; the negative case — one tenant predicate removed — is a pre-staged branch shown as its own CI run, because commenting out a predicate and rebuilding mid-demo is a restart, and a restart is a reset. **(2)** A receipt verifies on an air-gapped laptop with the gateway stopped; change one character and it fails. **(3)** `UPDATE` one byte of an `audit_events` payload and the verifier names the exact broken sequence number. **(4)** An admin attempts a high-sensitivity egress, gets STEP_UP plus a required distinct approver, cannot self-approve, and the receipt names both humans and both authenticators. **(5)** Stop the ledger: low-sensitivity views keep working, high-sensitivity export denies with `dependency_down` in the trace; time out the risk service and watch the tier forced to high. **(6)** Revoke an artist mid-session and watch the cascade — the API returns **seven counted steps**, not eight: credential, sessions, devices, grants, approvals, content URLs, identity trust. The eighth step in `revocation.ts` is the audit event and the ledger enqueue, which returns an `auditEventId` rather than a count, and that is the step worth pointing at, because it is the one that makes the other seven provable. A live brokered URL dies in front of the room. **(7)** Rotate the signing key and the tenant KEK: old receipts still verify under the retired `kid`, every DEK re-wraps, no ciphertext moves — on a demo corpus of a few hundred assets, which is fast, and we say so rather than implying it is fast at ten million. **(8)** The k6 output, alongside the stated ceiling — one anchoring writer, per-tenant chain serialisation, and the throughput that follows.

Nine minutes across eight points is roughly sixty seconds each, which only works because every one of them is a command with an expected output, rehearsed, in week 14's stabilisation window. That is the point: every one is a thing you run, not a thing you claim. That distinction is the entire product.

## 9. What the critics said, and what changes

Two reviewers — one reading the code, one reading it as a facility's vendor-risk process would — agree on the same verdict from opposite ends: sections 2 through 6 are ready to build against, and sections 1, 7 and 8 model a product without modelling the transaction. That is correct, and it is fixable in this document rather than in a later one.

### 9.1 The company track, which is now a workstream

There is no vendor. That is the finding that outranks every technical one, and the response is not a paragraph in §8.3 — it is **Track V**, founder-owned, running from week 1 to signature, with its own deliverables and its own gate.

Week 1: `git init` and a first commit, before the CI workflow S0 assumes; a LICENSE file and a `license` field in all seven `package.json` files; an IP-assignment chain executed by all four contributors and a written position on the SIH problem statement and the university's claim, obtained in writing before any code is offered under Apache 2.0. Weeks 1–3: incorporation, a trademark search on "VAJRA" (a crowded mark — assume a second name is needed and budget for it), a bank account that can receive USD, LUT filing for export of services, W-8BEN-E, and quotes for cyber liability and technology E&O at $2–5M with additional-insured endorsement. Those quotes come **before** the rate card is fixed, because if no underwriter will write that policy for a pre-revenue vendor at a premium the price can absorb, the price is wrong and the topology is wrong, not the paperwork. Weeks 3–10: SIG-Lite and CAIQ completed, network and data-flow diagrams, port/protocol/egress-destination table, SDLC and vulnerability-management policies with remediation SLAs, personnel screening for everyone with production access, and a documented separation of duties that ends the bus factor of one across weeks 6–11. The pen test moves **before** signature, not after: a scoped test in week 10 against the S3 build, with a retest letter by week 15.

§8.2 gains a cost side directly under the rate card — salaries or opportunity cost for four people, per-tenant infra, KMS, anchoring, the ~$20–40k SOC 2 CPA fee, the $15–30k pen test, compliance-automation subscription, insurance premium, legal drafting — and a 14-week burn line with the funding source named. §8.2 also gains a support tier per package: coverage hours, severity definitions, response and restoration targets, service credits, a named escalation and a phone number. The internal SLOs in §6.6 become contractual terms with credits attached, or they are marketing. Three engineers cannot staff 24×7; the pilot therefore sells **16×5 with a 2-hour P1 response and a customer-controlled documented bypass**, and §1.4 gains a second success criterion measuring incorrectly blocked egresses and added minutes per delivery. A gate nobody can work around at 03:00 loses the champion in week three whatever the receipt says.

The calendar stops being double-booked. Engineering stays at 14 weeks with S4 split across three, the acceptance surface protected and the observability half named as the cut line. Signature moves to **week 18**, after the retest letter and the questionnaire, and first cash to month nine. The route there is the one the facility reviewer offered: a mutual NDA and an **unpaid six-week design-partner engagement from week 3** — sandbox tenant, synthetic assets, their hardware, their assessor sees the data flows, and the acceptance test is co-written. That engagement is also the answer to §8.4's missing reference plan: a blind case study cleared by their comms plus an assessor's referral, designed now, because content-security customers do not join logo walls.

### 9.2 Mechanisms that were promised and never designed

**Client-supplied context dies.** `RequestContextSchema` stops accepting `ip`, `geo`, `localHour` and `userAgent`. `buildDecisionInput()` derives the hour from server time in the tenant's timezone, the IP from `req.ip` behind a configured `trustProxy`, and geo from IP lookup or not at all. Anything client-asserted becomes an unweighted hint. Fifth row on the §8.7 kill list; prove-point 5 restated to cover scoring inputs, not just the dependency path.

**`apps/risk` is deleted, and `RISK_MODE=http` with it.** A second hardcoded copy of the weights under a comment saying they must stay in step is exactly the defect the signed `PolicyBundle` exists to remove. The local scorer reads `riskWeights` from the bundle. §1.6's fail-closed drill retargets to a fault-injected local driver.

**The custody broker gets a real mechanism.** Single-use and revocable are not presigned-URL properties, so the broker becomes **STS AssumeRole with a session policy** on AWS, and a **thin redirecting proxy** — 302 to a short-lived URL, one redemption per capability, revocation by refusing the redirect — on B2, Wasabi and MinIO. Per-provider capability matrix in S3, with the honest column saying which providers get true revocation and which get expiry-only. Range GETs and resumed multipart are enumerated in one receipt; a checkout that never calls `/custody/complete` closes as `incomplete` with no content hash rather than a partial one.

**Idempotency ships as a contract break alongside keyset paging.** `Idempotency-Key` with a stored response on `/v1/authorize`, `/v1/custody/checkout`, `/v1/approvals/:id/decide` and asset registration. The `deliverContent` race (`vault/service.ts:203-217`) becomes a conditional `UPDATE … WHERE content_used = false RETURNING`, and §4.7's finalization re-decide takes the same shape.

**Drift, time, escrow, obligations.** A nightly reconciliation walk over registered objects using the ingest connector's cursor, with `vajra_assets_drifted` beside `vajra_rows_on_retired_kek`, and stated bucket preconditions as an install gate: versioning on, object lock, deny-delete to the broker principal, checksum-on-upload. NTP with a stated ±2s skew tolerance in the issuer/validity check, `tenants.timezone` alongside `region`. §5.9 gains CERT-In's 6-hour clock, 180-day in-India log retention and clock sync as architecture, DPDP and GDPR notification clocks with an owner, a `security@` address, a coordinated-disclosure policy, and a published sub-processor register naming Rekor, the TSA, KMS, Slack, Entra and the OTLP endpoint — with Rekor publication requiring written customer approval. Every Evidence Pack staples the full JWKS and signed issuer history; source and keys go to an escrow agent, named in §8.3. An on-prem release channel, a 12-month support window per version, a CVE patch cadence, and a written forward/backward rule for `schemaVersion` and `engineVersion`. An `idp` dependency in `REQUIRED_DEPS`, with a bounded, audited, hardware-attested local approver fallback for an OIDC outage.

### 9.3 Contradictions, decided

PGlite RLS is **proven**; §8.8's "unproven assumption" is deleted and the week-3 spike becomes a four-hour regression test. Studio Oversight is **removed from the forecast and from §2.1's argument** — database-per-tenant is rejected on migration fan-out alone, and oversight ships later as evidence packs pushed to a studio tenant, never cross-tenant reads. The `revocation.ts` citations are `:21-64`. Eleven scenes, 56 checks, 58 tests — one number each, everywhere. The vault caps at **25 MB**; the 5 GB sentence is fiction and is struck. The forgeable window is **up to four hours**, matching the staleness alert. `vpc` requires customer-held AWS KMS; `local` is sandbox-only, and §5.1's strongest sentence is qualified accordingly. Approvals land on facility desktops, not phones. Watermark reference and transfer-tool provenance enter the v2 body as an `attachments` array with a Signiant webhook in S7, or §1.5 loses both paragraphs. The outbox failure mode is restated as the memoised `FabricLedger.health()` bug; the fix is unchanged. Topology **does** price, and §8.1 says so. The tender-threshold argument is dropped: a $144k first-year commitment goes to full vendor risk on day one.

**The acceptance test is rewritten.** It now reads: an auditor verifies, offline, the pack's content hashes, every signature, issuer and `kid` against the stapled trust root, the stapled chain-range evidence, and the stapled anchor inclusion proof — and the pack states which checks require a live tenant. Failure refunds the unearned fee and returns the evidence intact, with termination for convenience, an export format, deletion certification, and a written guarantee that receipts issued in the term stay verifiable after it.

### 9.4 The honest state of it

Confident: the isolation model, the per-tenant chain, the key hierarchy, the identity rebuild and the offline verifier are correctly specified and the seams to build them exist today. Sections 2 through 6 would survive an architecture review now.

Betting: that a facility will let a control plane sit in its egress path on a design-partner handshake before there is a SOC 2, a reference or a second customer — and that the six weeks of unpaid access buys the credibility the paperwork cannot.

Most likely to kill it: not the technology, and not procurement. It is the gap between month one and month nine with four people, no revenue and no stated funding. Every finding above adds work outside the repo, and the thing that ends this is running out of runway three weeks before the first signature.
